CHAPTER 11

アニメーション・トランジションシステム

CSSアニメーションは「画面を派手にする飾り」ではありません。ユーザーに今何が起きているかを伝えるための言語です。 この章では、なぜアニメーションが必要なのか、どんな速さ・どんな動き方が適切なのかをトークン（変数）として体系化し、 実装方法（Transition / Animation / View Transitions API）からアクセシビリティ配慮までを一気通貫で解説します。

🔰 初学者向け：そもそも transition と animation の違いは？

transition は「ある状態からある状態へ」変化する時の橋渡し役です。例えば、ボタンに :hover が当たった瞬間の色変化に使います。2つの状態（前と後）さえ指定すれば、間の動きはブラウザが自動補間してくれます。

animation（@keyframes）は、もっと自由な動きを「振り付け」できる仕組みです。0%地点・50%地点・100%地点…と細かく状態を指定でき、ループさせたり、ページを開いた瞬間に自動再生させたりできます。「2点間の単純な変化」なら transition、「複雑な一連の動き」なら animation、と覚えておくと選択に迷いません。

①11.1 アニメーションシステムの目的

優れたアニメーションには必ず「目的」があります。なんとなく動かすのではなく、以下の5つの役割のどれを果たすために動かすのかを、実装前に言語化する習慣をつけましょう。

📊 図11-1：アニメーションが果たすべき5つの役割

逆に言えば、この5つのどれにも当てはまらないアニメーション（例：ページを開いた瞬間に意味もなく要素が回転する）は、ユーザーの注意力を奪うだけのノイズになりがちです。実装の前に「このアニメーションは誰の何を助けるのか」を一言で説明できるか、自分に問いかけてみてください。

②11.2 イージング（Easing）システム

イージングとは「アニメーションの速度変化のカーブ」のことです。現実世界の物体は急に動き出して急に止まったりはせず、加速・減速を伴います。CSSのデフォルト挙動であるeaseのままでもそれっぽく見えますが、デザインシステムとしては用途別にイージングを定義し、一貫した「動きの質感」をプロダクト全体で統一することが重要です。

📊 図11-2：5種類のイージングと適した用途

🔰 初学者向け：覚え方のコツ

ease-out（出口がゆっくり）は「登場」に、ease-in（入口がゆっくり）は「退場」に使う、と覚えるのが一番簡単です。新しく現れる要素は最初は元気よく動き出し最後はそっと収まる方が自然に見え（ease-out）、消える要素は逆に最初はゆっくり、最後は加速して消えていく方が自然に見えます（ease-in）。迷ったら、まず ease-out を使ってみましょう。

tokens/easing.css
/* ===== イージングトークンの定義 ===== */
:root {
  /* 標準イージング */
  --ease-linear:     linear;
  --ease-in:         cubic-bezier(0.4, 0, 1, 1);
  --ease-out:        cubic-bezier(0, 0, 0.2, 1);
  --ease-in-out:     cubic-bezier(0.4, 0, 0.2, 1);

  /* ブランド固有のイージング */
  --ease-spring:     cubic-bezier(0.34, 1.56, 0.64, 1);  /* バネのような弾み */
  --ease-smooth:     cubic-bezier(0.25, 0.1, 0.25, 1);    /* なめらかな動き */
  --ease-anticipate: cubic-bezier(0.36, 0, 0.66, -0.56);  /* 少し引いてから進む */

  /* 物理ベースのイージング（Material Design 3） */
  --ease-emphasized:            cubic-bezier(0.2, 0, 0, 1);
  --ease-emphasized-decelerate: cubic-bezier(0.05, 0.7, 0.1, 1);
  --ease-emphasized-accelerate: cubic-bezier(0.3, 0, 0.8, 0.15);
  --ease-standard:              cubic-bezier(0.2, 0, 0, 1);
}

③11.3 デュレーション（Duration）システム

デュレーションは「動きの長さ」です。短すぎると気づかれず、長すぎるとユーザーを待たせてしまいます。経験則として、操作対象が画面内で小さいほど短く、画面全体が変わるほど長くするのが基本です。

📊 図11-3：用途別デュレーションの6段階スケール

tokens/duration.css
/* ===== デュレーショントークン ===== */
:root {
  --duration-instant:  0ms;
  --duration-fast:     100ms;
  --duration-normal:   200ms;
  --duration-slow:     300ms;
  --duration-slower:   500ms;
  --duration-slowest:  700ms;
}

④11.4 CSS Transition の完全ガイド

transition プロパティは「どのCSSプロパティを」「どれくらいの時間で」「どんな速度カーブで」「どれだけ遅らせて」変化させるかを宣言します。複数のプロパティを別々のタイミングで動かすこともでき、これによってアニメーションに「リズム」を作ることができます。

components/button.css
/* ===== transition の構文 ===== */
/* transition: プロパティ名 デュレーション イージング 遅延; */

.button {
  background: var(--color-action-primary);
  transform: scale(1);
  box-shadow: none;

  /* 複数プロパティを個別に制御 */
  transition:
    background-color var(--duration-fast)   var(--ease-out),
    transform        var(--duration-normal) var(--ease-spring),
    box-shadow       var(--duration-normal) var(--ease-out);
}

.button:hover {
  background: var(--color-action-primary-hover);
  transform: scale(1.02);
  box-shadow: 0 4px 16px rgba(108, 71, 255, 0.3);
}

GPUが扱えるプロパティだけを動かす

ブラウザの描画パイプラインには「軽い処理」と「重い処理」があります。transform と opacity は GPU の合成（コンポジット）処理だけで完結するため非常に滑らかに動きますが、width・height・top・left などはレイアウト全体の再計算（リフロー）を引き起こし、カクつきの原因になります。

プロパティ種別該当プロパティ例処理コスト推奨度
合成（Composite）のみtransform / opacity / filter / clip-path低（GPU処理）✅ 推奨
ペイントが発生background-color / color / box-shadow中△ 許容範囲
レイアウトが再計算width / height / top / left / margin / padding高（リフロー発生）❌ 非推奨
components/menu.css
/* NG: レイアウトに影響するプロパティをアニメーション */
.menu {
  height: 0;
  transition: height 300ms ease; /* レイアウト再計算が毎フレーム発生 */
}
.menu.is-open { height: 200px; }

/* OK: transform + opacity でアニメーション */
.menu {
  opacity: 0;
  transform: translateY(-8px);
  transition:
    opacity   200ms var(--ease-out),
    transform 200ms var(--ease-out);
  pointer-events: none;
}
.menu.is-open {
  opacity: 1;
  transform: translateY(0);
  pointer-events: auto;
}

⑤11.5 CSS Animation（@keyframes）の完全ガイド

@keyframes は0%〜100%の間に好きなだけ中間状態を定義できる仕組みです。ローディングスピナーの回転、エラー時のシェイク（揺れ）、注目を集めるパルスなど、単純な「前後の変化」では表現できない動きに使います。

animations/keyframes.css
/* ===== @keyframes の定義 ===== */

/* フェードイン */
@keyframes fade-in {
  from { opacity: 0; }
  to   { opacity: 1; }
}

/* スライドアップ */
@keyframes slide-up {
  from {
    opacity: 0;
    transform: translateY(16px);
  }
  to {
    opacity: 1;
    transform: translateY(0);
  }
}

/* ローディングスピナー */
@keyframes spin {
  from { transform: rotate(0deg); }
  to   { transform: rotate(360deg); }
}

/* パルス（注目を引く） */
@keyframes pulse {
  0%, 100% { transform: scale(1); opacity: 1; }
  50%      { transform: scale(1.05); opacity: 0.8; }
}

/* シェイク（エラー通知） */
@keyframes shake {
  0%, 100% { transform: translateX(0); }
  20%      { transform: translateX(-8px); }
  40%      { transform: translateX(8px); }
  60%      { transform: translateX(-4px); }
  80%      { transform: translateX(4px); }
}

/* ===== animation プロパティの構文 ===== */
.element {
  /* animation: 名前 デュレーション イージング 遅延 回数 方向 フィルモード 再生状態 */
  animation: slide-up 300ms var(--ease-out) 0ms 1 normal both running;
}

/* ===== ユーティリティクラスとして定義 ===== */
.animate-fade-in  { animation: fade-in  200ms var(--ease-out) both; }
.animate-slide-up { animation: slide-up 300ms var(--ease-out) both; }
.animate-spin     { animation: spin     1s    var(--ease-linear) infinite; }
.animate-pulse    { animation: pulse    2s    var(--ease-in-out) infinite; }
.animate-shake    { animation: shake   400ms  var(--ease-out) both; }
サブプロパティ役割主な値
animation-iteration-count繰り返し回数1 / 3 / infinite
animation-direction再生方向normal / reverse / alternate
animation-fill-mode開始前・終了後の状態保持forwards（最後を維持）/ backwards（最初から）/ both
animation-play-state再生・停止の制御running / paused

⑥11.6 View Transitions API（ページ遷移アニメーション）

View Transitions API は、ページ遷移やDOM更新の前後でブラウザが自動的にスクリーンショットを撮り、滑らかにクロスフェード・モーフィングしてくれるモダンAPIです（Chrome 111+、Safari 18+対応）。これまでJavaScriptで複雑に実装していた「要素が次のページでも同じ場所に存在し続けているように見せる」演出が、CSSの数行で実現できます。

view-transitions.css
/* ===== View Transitions API ===== */

/* デフォルトのクロスフェードをカスタマイズ */
::view-transition-old(root) {
  animation: fade-out 200ms var(--ease-in) both;
}

::view-transition-new(root) {
  animation: fade-in 300ms var(--ease-out) both;
}

@keyframes fade-out {
  from { opacity: 1; }
  to   { opacity: 0; }
}

/* ===== 要素レベルの遷移 ===== */
.hero-image {
  view-transition-name: hero;  /* ユニークな名前を設定 */
}

::view-transition-old(hero),
::view-transition-new(hero) {
  animation-duration: 400ms;
  animation-timing-function: var(--ease-emphasized);
}
router.js
// View Transitions API の使用例
async function navigateTo(url) {
  if (!document.startViewTransition) {
    window.location.href = url;
    return;
  }

  document.startViewTransition(async () => {
    const response = await fetch(url);
    const html = await response.text();
    document.documentElement.innerHTML = html;
    window.history.pushState({}, '', url);
  });
}
⚠️ 注意：非対応ブラウザへのフォールバック

document.startViewTransition の存在チェックを必ず行いましょう。未対応ブラウザでは即座に通常のページ遷移にフォールバックさせることで、機能の有無に関わらず操作自体は破綻しないようにします（プログレッシブ・エンハンスメント）。

⑦11.7 アクセシビリティへの配慮

前庭障害（めまいや乗り物酔いに似た症状）を持つユーザーにとって、過剰なアニメーションは単なる好みの問題ではなく、健康上の問題になり得ます。OSの「視差効果を減らす」設定（prefers-reduced-motion）は、CSSで必ず尊重しましょう。これは「やった方が良い」ではなく「やらなければならない」アクセシビリティ要件です。

accessibility/motion.css
/* ===== prefers-reduced-motion: アニメーション削減設定を必ず尊重する ===== */

/* 方法1: メディアクエリで上書き */
.animated-element {
  animation: slide-up 300ms var(--ease-out) both;
}

@media (prefers-reduced-motion: reduce) {
  .animated-element {
    animation: fade-in 150ms ease both; /* 動きを排除してフェードのみに */
  }
}

/* 方法2: カスタムプロパティで制御（推奨） */
:root {
  --motion-duration-normal: 200ms;
  --motion-easing-default:  var(--ease-out);
}

@media (prefers-reduced-motion: reduce) {
  :root {
    --motion-duration-normal: 0ms; /* 全てのアニメーションを瞬時に */
  }
}

.button {
  transition: background-color var(--motion-duration-normal) var(--motion-easing-default);
}
🔰 初学者向け：方法2が推奨される理由

方法1（個別の@media上書き）は要素1つずつにメディアクエリを書く必要があり、規模が大きくなると漏れが発生しがちです。方法2はカスタムプロパティ自体を1箇所で 0ms に切り替えるだけで、それを参照している全てのコンポーネントに一括反映できます。デザインシステム全体に展開するなら方法2を基本方針にしましょう。

⑧11.8 ベストプラクティス

✅ アニメーション設計のベストプラクティス
👍 DO
  • ユーザー操作への明確なフィードバックとして使う
  • コンテンツの変化（追加・削除・並び替え）を補足説明する
  • transform・opacity を中心に組み立てる
  • prefers-reduced-motion を必ず尊重する
  • アニメーション開始直前に will-change を設定する
👎 DON'T
  • 意味のない装飾だけのページロードアニメーション
  • ユーザーを待たせるだけの長いロード演出
  • 100ms以下の微細な動きを乱用する
  • ループし続けて注意を散らすアニメーション
  • *{ will-change: transform; } のような全要素への適用
will-change.css
/* GPU レイヤーに事前昇格させてカクつきを防ぐ */
.modal {
  will-change: transform, opacity; /* アニメーション開始前に設定 */
}

/* アニメーション終了後は外す（メモリを解放） */
.modal.animation-done {
  will-change: auto;
}

/* NG: すべての要素に適用（過剰なメモリ消費） */
* { will-change: transform; }

CHAPTER 12

CSSアーキテクチャパターン

CSSには「コンパイルエラー」がありません。書けば書くだけ、矛盾したルールがあっても黙って動いてしまいます。 だからこそ、プロジェクト全体でCSSをどう整理し、どう詳細度を管理するかという設計方針＝CSSアーキテクチャが、 チーム開発の生命線になります。本章では代表的な4つのアプローチを比較し、選定基準を提示します。

🔰 初学者向け：なぜCSSは「荒れやすい」のか

CSSのルールは基本的に「後に書いたものが勝つ」「より詳細なセレクタが勝つ」という単純な仕組みで動いています。これはシンプルですが、ファイル数が増えチームの人数が増えると「なぜこの色が反映されないのか分からない」「!important だらけになってしまった」という事態を招きます。CSSアーキテクチャとは、この力学を事前にルール化し、誰が書いても秩序が保たれる仕組みを作ることです。

📊 図12-1：代表的な5つのCSSアーキテクチャ

①12.1 ITCSS（Inverted Triangle CSS）

Harry Roberts が考案した、詳細度の低いものから高いものへ順番にCSSファイルを積み上げていくアーキテクチャです。「逆三角形」という名前の通り、上から下に行くほどセレクタの詳細度が高く、適用範囲が狭くなります。レイヤーの順番さえ守れば、原則として !important は不要になります。

🔰 初学者向け：接頭辞（プレフィックス）の意味

ITCSSではよく .o-（Object）・.c-（Component）・.u-（Utility）のような接頭辞をクラス名に付けます。これはクラス名を見ただけで「これはレイアウト用か、コンポーネントか、上書き用ユーティリティか」が一目で分かるようにするための慣習です。命名規則自体がドキュメントの役割を果たします。

②12.2 CUBE CSS

Andy Bell が提案した、Composition（構成）・Utility（ユーティリティ）・Block（ブロック）・Exception（例外） の4層からなるアーキテクチャです。ITCSSよりも軽量で、特に「コンポーネント単位のバリアント管理」に強みがあります。

📊 図12-3：CUBE CSSの4層構造

  data-variant="primary"
  data-size="lg"
  href="/get-started"
>
  始める

/* Block: コアスタイル */
.button {
  display: inline-flex;
  align-items: center;
  gap: var(--space-2);
  border-radius: var(--radius-md);

  color: var(--color-action-primary);

  padding-inline: var(--space-6);
  font-size: var(--font-size-base);

🔰 初学者向け：なぜ data属性でバリアントを管理するの？

従来は .button--primary・.button--lg のようにクラスを複数組み合わせる（BEMのModifier）方法が主流でした。data属性方式の利点は、「バリアント＝コンポーネントの状態」という意味がHTMLを見ただけで明確になることと、JavaScriptから el.dataset.variant で簡単に読み書きできることです。どちらが正解というわけではなく、チームの好みやツールチェーンとの相性で選びます。

③12.3 CSS Layers（@layer）

CSS Cascade Layers（@layer）は、詳細度の戦争を終わらせるためにW3Cが標準化した仕組みで、2022年までに全モダンブラウザで利用可能になりました。レイヤー間では「セレクタの詳細度」よりも「レイヤーの宣言順」が優先されるため、ユーティリティクラスのような単純なセレクタでも、複雑なセレクタのコンポーネントスタイルに確実に勝てるようになります。

📊 図12-4：@layer の宣言順がそのまま優先順位になる

layers.css
/* ===== @layer の宣言（順序を最初に定義） ===== */
@layer reset, base, tokens, objects, components, utilities;

/* ===== 各レイヤーへの割り当て ===== */
@layer reset {
  *, *::before, *::after { box-sizing: border-box; }
  * { margin: 0; }
}

@layer tokens {
  :root {
    --color-primary: #6C47FF;
    --space-4: 16px;
  }
}

@layer components {
  .button {
    background: var(--color-primary);
    padding: var(--space-2) var(--space-4);
  }
}

@layer utilities {
  /* utilities は詳細度が低くても components に勝つ */
  .bg-transparent { background: transparent !important; }
  .hidden { display: none; }
}

/* ===== レイヤー外のスタイルは常に最強 ===== */
.override { color: red; } /* レイヤーに属さないので全レイヤーに勝つ */
⚠️ 落とし穴：レイヤー外のCSSは常に最優先

@layer に属さない通常のCSSルールは、どのレイヤーよりも強い詳細度を持ちます。サードパーティのCSS（外部ライブラリのスタイルなど）が @layer の外側に書かれている場合、自分たちの utilities レイヤーで上書きしようとしても効かないことがあるため注意が必要です。

CHAPTER 13

デザイントークン

デザイントークンとは、色・スペース・タイポグラフィなどのデザインの意思決定を、特定のプラットフォームに依存しない形式で1箇所に保存したものです。 JSONで一度定義すれば、CSS・iOS・Android・Figmaなど、あらゆる出力先に自動変換できます。「デザインとコードの真実の源（Single Source of Truth）」を作る取り組みだと考えてください。

📊 図13-1：1つのトークン定義から複数プラットフォームへ展開

🔰 初学者向け：CSS変数とデザイントークンは何が違うの？

CSS変数（カスタムプロパティ）は「CSSの中だけ」で使える仕組みです。一方デザイントークンはもっと広い概念で、「色は#6C47FF」という決定そのものをJSONなどの中立な形式で管理し、そこからCSS変数・Swiftのコード・Androidのリソースファイルなど複数の出力を自動生成するための「元データ」を指します。つまり、CSS変数はデザイントークンを実現する手段の一つです。

①13.1 W3C Design Tokens 仕様

W3Cが標準化を進めるデザイントークンのJSON形式です。各値は $value（実際の値）と $type（値の種類：色・寸法・デュレーションなど）を持ち、{color.purple.500} のような中括弧記法で他のトークンを参照（エイリアス化）できます。

tokens/primitive.tokens.json
{
  "color": {
    "purple": {
      "50":  { "$value": "#f5f3ff", "$type": "color" },
      "500": { "$value": "#6C47FF", "$type": "color" },
      "900": { "$value": "#1e0a5c", "$type": "color" }
    },
    "action": {
      "primary": {
        "$value": "{color.purple.500}",
        "$type": "color",
        "$description": "メインのアクションカラー（ボタン・リンクなど）"
      }
    }
  },
  "spacing": {
    "4": { "$value": "16px", "$type": "dimension" },
    "6": { "$value": "24px", "$type": "dimension" }
  },
  "font-size": {
    "base": { "$value": "1rem", "$type": "dimension" },
    "lg":   { "$value": "1.125rem", "$type": "dimension" }
  },
  "duration": {
    "fast":   { "$value": "100ms", "$type": "duration" },
    "normal": { "$value": "200ms", "$type": "duration" }
  },
  "border-radius": {
    "md": { "$value": "8px",  "$type": "dimension" },
    "lg": { "$value": "12px", "$type": "dimension" }
  }
}

ポイントは color.action.primary が直接 #6C47FF を持たず、{color.purple.500} というエイリアスで参照している点です。これにより、もしブランドカラーが変わっても color.purple.500 の1箇所を変えるだけで、それを参照している全てのセマンティックトークンに変更が波及します。

🔰 初学者向け：プリミティブとセマンティックの違い

プリミティブトークンは「生の値」です（purple.500 = #6C47FF）。セマンティックトークンは「その値が何の役割を持つか」を表します（color.action.primary = purple.500）。コンポーネントのCSSでは必ずセマンティックトークン（--color-action-primary）を参照し、プリミティブ（--color-purple-500）を直接使わないようにすると、後でブランドカラーやダークモード切り替えをする際に変更箇所が劇的に少なくなります。

④14.4 JavaScript実装（アクセシブル）

見た目だけでなく「キーボードだけで完結して操作できるか」がアクセシブルなModalの鍵です。開いた時に最初の要素へフォーカスを移し、Tabキーがモーダルの外に出ないように「フォーカストラップ」を実装し、閉じた時には元いた場所にフォーカスを戻す、という3点が必須要件です。

modal.js
class Modal {
  #modal;
  #trigger;
  #focusableElements;
  #previouslyFocused;

  constructor(modalId) {
    this.#modal   = document.getElementById(modalId);
    this.#trigger = document.querySelector(`[data-modal-trigger="${modalId}"]`);
    if (!this.#modal || !this.#trigger) return;
    this.#init();
  }

  #init() {
    this.#trigger.addEventListener('click', () => this.open());

    this.#modal.querySelectorAll('[data-modal-close]').forEach(el => {
      el.addEventListener('click', () => this.close());
    });

    this.#modal.addEventListener('keydown', (e) => {
      if (e.key === 'Escape') this.close();
      if (e.key === 'Tab')    this.#trapFocus(e);
    });
  }

  open() {
    this.#previouslyFocused = document.activeElement;

    this.#modal.removeAttribute('hidden');
    this.#modal.removeAttribute('aria-hidden');

    requestAnimationFrame(() => {
      this.#modal.classList.add('is-open');
    });

    this.#getFocusableElements();
    this.#focusableElements[0]?.focus();

    document.body.style.overflow = 'hidden';
  }

  close() {
    this.#modal.classList.remove('is-open');

    const duration = getComputedStyle(this.#modal)
      .getPropertyValue('--modal-duration').trim();
    const ms = parseFloat(duration) * (duration.endsWith('s') && !duration.endsWith('ms') ? 1000 : 1);

    setTimeout(() => {
      this.#modal.setAttribute('hidden', '');
      this.#modal.setAttribute('aria-hidden', 'true');
      document.body.style.overflow = '';
      this.#previouslyFocused?.focus();
    }, ms);
  }

  #getFocusableElements() {
    this.#focusableElements = [
      ...this.#modal.querySelectorAll(
        'a[href], button:not([disabled]), textarea, input, select, [tabindex]:not([tabindex="-1"])'
      ),
    ];
  }

  #trapFocus(e) {
    if (!this.#focusableElements.length) return;
    const first = this.#focusableElements[0];
    const last  = this.#focusableElements[this.#focusableElements.length - 1];

    if (e.shiftKey && document.activeElement === first) {
      last.focus();
      e.preventDefault();
    } else if (!e.shiftKey && document.activeElement === last) {
      first.focus();
      e.preventDefault();
    }
  }
}

モーダルが開いている間に Tab キーを押し続けると、本来は背後のページの要素にもフォーカスが移動してしまいます。これではユーザーが「今どこを操作しているか」見失ってしまいます。フォーカストラップは、モーダル内の最後の要素で Tab を押したら最初の要素に、最初の要素で Shift+Tab を押したら最後の要素にフォーカスを戻すことで、フォーカスをモーダルの中だけに「閉じ込める」仕組みです。

⚠️ 落とし穴：アニメーション完了前に hidden を付けてしまう

閉じる処理で classList.remove('is-open') と同時に hidden 属性を付けてしまうと、CSSのトランジションが始まる前に要素が消えてアニメーションが機能しません。上記の実装のように setTimeout でアニメーション時間（--modal-duration）の分だけ待ってから hidden を付与するようにしましょう。

✅ コンポーネント実装のベストプラクティス
👍 DO
  • 状態遷移図を先に書いてから実装に入る
  • 開閉時にフォーカスを正しく移動・復元する
  • Escキー・背景クリックの両方で閉じられるようにする
  • CSSのデュレーション値をJS側でも参照し二重管理を避ける
👎 DON'T
  • マウス操作だけを前提に実装する
  • display: none だけで開閉しアニメーションを諦める
  • 背景のスクロールをロックし忘れる
  • モーダルを開いたままbodyの内容を読み上げ可能にしておく
CHAPTER 15

パフォーマンス最適化

どれだけ美しいデザインシステムを構築しても、表示が遅ければユーザーは離脱してしまいます。 本章では、ブラウザがCSSをどう処理しているかという基礎から、クリティカルCSS・ロード最適化・セレクタ効率・バンドルサイズ削減、 そしてGoogleの品質指標であるCore Web Vitalsとの関係までを解説します。

①15.1 CSSパフォーマンスの基礎：レンダリングパイプライン

ブラウザは画面を表示するまでに6つの段階を経ます。どの段階で再計算が起きるかによって処理コストが大きく異なり、レイアウト（Layout）の再計算が最も重く、合成（Composite）だけで済む変更が最も軽いという覚えておくべき序列があります。

📊 図15-1：レンダリングパイプラインと各段階の処理コスト

🔰 初学者向け：「リフロー」「リペイント」って何？

「リフロー」は要素のサイズや位置を再計算すること、「リペイント」は色や見た目を塗り直すことです。width を変えると要素の大きさが変わるので、それに引っ張られて周囲の要素も配置し直す必要があり「リフロー」が起きます。一方 transform で要素を動かしても、他の要素のレイアウトには一切影響しないため、リフローもリペイントも起きずGPUの合成だけで完結します。第11章で「transform・opacityを使う」と繰り返し強調していたのは、まさにこの仕組みが理由です。

②15.2 クリティカルCSS

通常、ブラウザは<link rel="stylesheet">でCSSファイル全体をダウンロードし終えるまで、画面の描画をブロックします。CSSファイルが数百KBある場合、ユーザーは真っ白な画面を見続けることになります。クリティカルCSSとは、最初に見える範囲（ファーストビュー、Above the fold）のスタイルだけを抜き出してHTMLに直接埋め込み、即座に描画を開始させるテクニックです。

📊 図15-2：クリティカルCSSによるレンダリングブロック回避

index.html
<head>
  <!-- Above the fold のCSSをインラインに -->
  <style>
    :root { --color-bg-base: #fafafa; --color-text-primary: #18181b; }
    body { font-family: system-ui, sans-serif; background: var(--color-bg-base); margin: 0; }
    .header { display: flex; align-items: center; height: 64px; padding: 0 24px; }
    .hero { padding: 80px 24px; text-align: center; }
  </style>

  <!-- 残りのCSSは非同期ロード -->
  <link
    rel="preload"
    href="/styles/main.css"
    as="style"
    onload="this.onload=null;this.rel='stylesheet'"
  >
  <noscript><link rel="stylesheet" href="/styles/main.css"></noscript>
</head>

③15.3 CSSのロード最適化

フォントのプリロード、メディアクエリによる条件付きロード、可変フォント（Variable Fonts）の活用に加え、モダンCSSの contain と content-visibility を使うことで、ブラウザに「ここはレンダリングを省略してよい」というヒントを与えられます。

index.html
<head>
  <!-- 使用するフォントファイルを事前にロード -->
  <link rel="preload" href="/fonts/Inter-var.woff2" as="font" type="font/woff2" crossorigin>
  <link rel="preload" href="/fonts/NotoSansJP-Regular.woff2" as="font" type="font/woff2" crossorigin>
</head>

<!-- メディアクエリで条件ロード -->
<link rel="stylesheet" href="print.css" media="print">
<link rel="stylesheet" href="mobile.css" media="(max-width: 768px)">
fonts.css
/* ===== @font-face の最適化 ===== */
@font-face {
  font-family: 'Inter';
  src: url('/fonts/Inter-var.woff2') format('woff2');
  font-weight: 100 900;          /* 可変フォント：1ファイルで複数ウェイトをカバー */
  font-style: normal;
  font-display: swap;            /* FLASHを防ぎ、FOUTを許容 */
  unicode-range: U+0000-00FF, U+0131; /* 使用する文字範囲のみ */
}

/* ===== contain プロパティ: ブラウザの最適化ヒント ===== */
.widget {
  contain: layout style; /* この変更が外部レイアウトに影響しないことを宣言 */
}

.card-list {
  contain: strict; /* layout + style + paint + size */
}

/* ===== content-visibility: 画面外要素のレンダリングをスキップ ===== */
.article-card {
  content-visibility: auto;             /* 画面外はレンダリングスキップ */
  contain-intrinsic-size: auto 400px;  /* スキップ時の推定サイズ（レイアウトシフト防止） */
}
用語意味
FOUT (Flash of Unstyled Text)フォント読み込み中は代替フォントで表示し、読み込み完了後に切り替わる現象
FOIT (Flash of Invisible Text)フォント読み込みが完了するまでテキストが非表示になる現象（避けるべき）
font-display: swapFOITを避け、即座に代替フォントで表示してから本番フォントへ差し替える設定

④15.4 CSSセレクタのパフォーマンス

ブラウザはセレクタを右から左に評価します。つまり .header ul li a というセレクタがあれば、まず全ての a 要素を見つけ出してから、その親が liか、さらにその親がulか…と遡って絞り込みます。右端（キーセレクタ）が広すぎると、無駄な走査が大量に発生します。

selectors.css
/* NG: 右端が広すぎるセレクタ（多くの要素にマッチして走査が重い） */
.page .content * { color: inherit; }        /* * は全要素にマッチ */
.sidebar div + div { margin-top: 8px; }      /* 全divを走査 */
.header ul li a { color: var(--link); }      /* 深いネスト */

/* OK: 具体的なクラスセレクタ（マッチが速い） */
.sidebar__item { margin-top: 8px; }
.nav__link { color: var(--link); }

/* ===== :is() / :where() で冗長な繰り返しを排除 ===== */

/* NG: 同じスタイルの繰り返し */
h1, h2, h3, h4, h5, h6 { font-weight: 600; }

/* OK: :is() でまとめる（詳細度は引数の中で最も高いもの） */
:is(h1, h2, h3, h4, h5, h6) { font-weight: 600; }

/* :where() は詳細度0のため上書きしやすい */
:where(h1, h2, h3, h4, h5, h6) { font-weight: 600; }

⑤15.5 CSSバンドルサイズの最適化

未使用のCSSを検出して削除する PurgeCSS、そして高速なRust製CSS処理系である Lightning CSS を組み合わせることで、本番ビルドのファイルサイズを大幅に削減できます。動的に付与されるクラス名（例：JSで追加されるis-open）は誤って削除されないよう、セーフリストへの登録が必須です。

postcss.config.js
/* ===== PurgeCSS: 未使用CSSの削除 ===== */
export default {
  plugins: {
    '@fullhuman/postcss-purgecss': {
      content: [
        './src/**/*.html',
        './src/**/*.jsx',
        './src/**/*.tsx',
        './src/**/*.vue',
      ],
      defaultExtractor: (content) =>
        content.match(/[\w-/:]+(?<!:)/g) || [],
      /* セーフリスト: 動的に追加されるクラスは削除しない */
      safelist: {
        standard: ['is-open', 'is-loading', 'is-error'],
        patterns: [/^animate-/, /^modal/],
      },
    },
  },
};
vite.config.js

import { defineConfig } from 'vite';

  css: {
    transformer: 'lightningcss',    /* Rust製の超高速CSS処理ツール */

⑥15.6 Core Web Vitalsとの関係

Core Web Vitals は Google が定める3つの品質指標で、検索順位にも影響します。CSSの書き方一つで、これらの数値は大きく改善できます。

📊 図15-3：Core Web Vitals 3指標とCSS視点での改善策

HTML側で width と height 属性（または srcset）を適切に指定し、CSS側で width: 100%; height: auto; を指定することで、モダンブラウザは自動的に画像のアスペクト比を計算し、表示領域を事前に確保（CLSを防止）します。

⚠️ 注意：attr() によるアスペクト比指定は避ける

かつて一部の例で見られた aspect-ratio: attr(width) / attr(height) のようなCSSでの attr() 関数を用いたアスペクト比の動的指定は、実験的な仕様であり、多くのブラウザでサポートされていません。これを記述すると、非サポート環境でアスペクト比が正しく適用されない（または無視される）リスクがあります。そのため、HTML側の属性でアスペクト比の情報をブラウザに提供するのが最も安全で確実なCLS対策です。

cls-prevention.css
/* ===== CLS 対策: 画像にサイズ（アスペクト比）を確保する ===== */
img {
  /* HTML側で width="..." height="..." を指定し、CSSで以下を適用します。
     ブラウザが自動的にアスペクト比（auto width / height）を計算し、領域を確保します。 */
  width: 100%;
  height: auto;
}

/* ===== CLS 対策: カスタムフォントのレイアウトシフト軽減 ===== */
/* size-adjust で代替フォントのサイズを本番フォントに近づける */
@font-face {
  font-family: 'InterFallback';
  src: local('Arial');
  size-adjust: 107%;       /* InterとArialのサイズ差を調整 */
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}
✅ パフォーマンス最適化のベストプラクティス
👍 DO
  • ファーストビューのCSSはインライン化する
  • 画像・動画には常に width/height を指定する
  • 画面外コンテンツに content-visibility: auto を活用する
  • 本番ビルドで未使用CSSを自動的にパージする
👎 DON'T
  • 深くネストした非効率なセレクタを多用する
  • サイズ未指定の画像・広告枠を埋め込む
  • 実験的なCSS機能（attr()のアスペクト比利用等）に依存する
  • 全CSSを1つの巨大ファイルとして同期ロードする

①16.1 Storybook：コンポーネントカタログ

Storybook は、コンポーネントを実際のアプリケーションから切り離して単独で表示・操作できる「カタログ」を作るツールです。デザイナーやQA担当者がコードを読まなくても全パターンを確認でき、コンポーネントのドキュメントとしても機能します。

🔰 初学者向け：Storybookがあると何が嬉しいの？

新しいボタンコンポーネントを作ったとき、それをアプリの本番画面に組み込まないと見た目を確認できないのは非効率です。Storybookでは variant="primary" や size="lg" のような全組み合わせを一覧表示でき、「ボタンの全パターン」を1ページで見渡せます。デザインレビューやアクセシビリティチェックもこの単位で完結できるため、チーム開発のコミュニケーションコストが大きく下がります。

Button.stories.tsx
import type { Meta, StoryObj } from '@storybook/react';
import { Button } from './Button';

    disabled: { control: 'boolean' },
    loading:  { control: 'boolean' },
  },

export const Primary: Story = {
  args: { variant: 'primary', size: 'md', children: '送信する' },
};

};

  args: { variant: 'primary', size: 'md', loading: true, children: '処理中...' },
