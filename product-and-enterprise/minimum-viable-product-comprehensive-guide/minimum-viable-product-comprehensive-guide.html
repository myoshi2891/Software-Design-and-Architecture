1. MVPとは何か

MVP（Minimum Viable Product / 最小実行可能製品）とは、「最小限の機能で最大限の学びを得るために構築するプロダクト」です。Eric Riesが著書「The Lean Startup」で提唱し、現代のプロダクト開発における根幹哲学となっています。

一言で言うと

「作りすぎず、学ぶための最小限のプロダクトを素早く届けて、顧客の反応から真実を学ぶ」手法です。

1.1 「M・V・P」それぞれの意味

Minimum（最小限）
機能を徹底的に絞り込む。余分な機能を一切含めず、必要最低限の機能だけを実装する。
Viable（実行可能）
ユーザーが実際に使える状態。コア価値を体験できる品質を備えている。
Product（製品）
プロトタイプではなく、実際にユーザーに届ける本物のプロダクト。

1.2 モックアップ・プロトタイプとの違い

種別動作対象目的
モックアップ・ワイヤーフレーム動作しない内部チームデザイン検証
プロトタイプ限定的に動作内部向け技術検証
MVP実際に動作実ユーザーへ提供市場検証

1.3 MVPが重要な理由：従来型開発との比較

MVPなし（従来型）
  • 完全な機能を1年かけて開発
  • リリース後に顧客が使わないと判明
  • 時間・コスト・機会を大量に損失
  • 競合に遅れをとる
MVPあり（リーン開発）
  • 最小機能を2〜3ヶ月で構築
  • 実ユーザーのフィードバックを取得
  • 必要な方向性が明確になる
  • 競合より早く市場参入できる

2. MVPの思想的背景：リーンスタートアップ

2.1 Build-Measure-Learn サイクル

MVPの中核にある考え方は、Build（構築）→ Measure（測定）→ Learn（学習）の高速サイクルです。このサイクルをいかに短くするかが、MVP成功の鍵となります。

2.2 検証済み学習（Validated Learning）

MVPでは「作った」ことではなく、「学んだ」ことが成果です。仮説を立て、実験し、データで検証するプロセスを繰り返します。

2.3 Innovation Accounting（イノベーション会計）

MVPの成果は従来の財務指標ではなく、「学習の進捗」で測定します。

従来の指標（避けるべき）
  • 総ユーザー数（見栄えが良いだけ）
  • ページビュー（行動に繋がらない）
  • フォロワー数（本質的価値なし）
リーン指標（Actionable Metrics）
  • 顧客獲得コスト（CAC）
  • 顧客生涯価値（LTV）
  • リテンション率（継続率）
  • 機能の実際の使用率
  • NPS（顧客推奨度）

4. 問題発見と顧客検証

最重要ステップ

MVPを作る前に「本当に解くべき問題があるか」を確認することが最重要です。コードを書く前にインタビューを行うことで、誰も使わないものを作るリスクを大幅に減らせます。

4.2 顧客インタビューのベストプラクティス

やるべきこと（DO）
  • 過去の行動について聞く「以前この問題をどう解決しましたか？」
  • 具体的な事例を聞く「最後にそれが起きたのはいつですか？」
  • 感情を掘り下げる「そのときどう感じましたか？」
  • 沈黙を活用する。相手が考える時間を与える
  • 「なぜ？」を3〜5回繰り返して根本原因を探る
やってはいけないこと（DON'T）
  • ソリューションを説明する「こんな機能があったら使いますか？」
  • Yes/Noで答えられる質問をする「この問題は困りますか？」
  • 未来の行動を聞く「もし〇〇があったら使いますか？」
  • インタビューで自分のアイデアを正当化しようとする

5. MVPのスコープ定義

5.1 Jobs-to-be-Done（JTBD）フレームワーク

機能リストではなく、「ユーザーが何を達成しようとしているか」を中心に考えます。JTBDは「状況・動機・期待する結果」の3要素で構成されます。

JTBD例：「毎朝の通勤電車で（状況）/ 英語を効率的に学習したい（動機）/ TOEICスコアを上げられるように（結果）」

5.2 機能優先順位付け：MoSCoW法

MVPに含める機能を4つのカテゴリで分類し、Must Have のみをMVPに含めます。

7. 技術スタック選定

7.1 選定の判断基準（優先順）

1
開発速度
チームが最も習熟している技術を選ぶ。新しい技術の習得コストはMVPフェーズでは致命的な遅延になる。
2
チームスキル
チーム全員が使えるか、採用市場での人材が豊富かを確認する。
3
エコシステムの充実度
ライブラリ・ツールが充実し、コミュニティが活発であること。
4
コスト最小化
無料ティアを最大活用。Vercel・Supabase・Railway等はMVPを無料で運用できる。

8. MVP実装のベストプラクティス

8.1 コーディング原則

YAGNI原則
You Aren't Gonna Need It。今必要でない機能は実装しない。将来の妄想より現在の問題を解く。
KISS原則
Keep It Simple, Stupid。複雑な設計より単純な解決策。シンプルなコードが保守しやすい。
完璧より完成
Done is Better than Perfect。完成度80%でリリース。残り20%はユーザーが教えてくれる。
意図的な技術負債
意識的な技術的負債はOK。ただし文書化し、期限を設けて管理すること。無意識の負債は避ける。

早期にCI/CDを整備することで、迅速なイテレーションが可能になります。

CI/CDパイプライン：コードをpushするだけでテスト・デプロイが自動実行される
# .github/workflows/ci.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint        # ESLintチェック
      - run: npm run type-check  # TypeScript型チェック
      - run: npm test            # ユニットテスト実行
      - run: npm run build       # ビルド確認

  deploy-preview:
    if: github.event_name == 'pull_request'
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Vercel Preview
        run: npx vercel --token=${{ secrets.VERCEL_TOKEN }}

8.3 セキュリティ最低限チェックリスト

  • HTTPS 必須 — HTTPは絶対に使わない。Let's Encrypt / CDNで無料化できる。
  • 環境変数で秘密情報を管理 — コードにAPIキーを絶対に書かない。.env.local / secrets managerを使う。
  • パスワードハッシュ化 — bcrypt / argon2を使用する。MD5・SHA1は禁止。
  • SQLインジェクション対策 — ORMを使い、生SQLを避ける。パラメータバインドを徹底する。
  • CORS設定 — 許可するオリジンを明示。ワイルドカード（*）は避ける。
  • レート制限 — APIエンドポイントに上限を設定。DDoS・ブルートフォース対策。
  • 依存関係の脆弱性スキャン — npm audit / pip-audit。GitHub Dependabotを活用。

8.4 テスト戦略：MVPでのテスト優先度

テストピラミッド：ユニットテストを最も重視し、E2Eテストは最小限に絞る
MVPのテスト原則

完全なテストカバレッジは求めない。ビジネスロジックの中核だけをカバーし、リグレッション（意図しないバグの再発生）を防ぐための最小限のテストを書くことが目標です。

  • サポートチケット分析

プロダクトNorth Star Metricその理由

Spotify1日あたりの楽曲再生時間継続的なエンゲージメントを測る
あなたのMVPコア価値が生まれた回数プロダクトがユーザーにとって本質的な価値を届けた瞬間を数える

10.2 ピボットの主要な種類

種類説明有名な事例
ズームイン・ピボット1機能が製品全体になるTwitterは元々Odeoというポッドキャスト会社の一機能だった
ズームアウト・ピボット1製品が1機能になる他の大きな製品の一部として組み込まれる
顧客セグメント・ピボット同じ問題を抱える別の顧客層へ解決策はそのままに対象ユーザーを変える
顧客ニーズ・ピボット同じ顧客の別の問題を解く深く知った顧客から別のニーズを発見する
プラットフォーム・ピボットアプリ↔プラットフォームの転換サービスをAPIとして提供する形に変える
ビジネスモデル・ピボット収益化の方法を変える無料→有料 / B2C→B2B への転換
ピボットの心得

ピボットは「失敗」ではありません。間違いに気づいたら素早く方向転換することが、MVPの目的そのものです。多くの成功したスタートアップ（Slack, Instagram, YouTube）はピボットによって生まれました。

13. MVP開発の黄金律 10箇条

1
コードを書く前に検証する
仮説を立てて→インタビューで確認。問題を確認してからソリューションを作る。コードより対話を先に。
2
機能は3回絞り込む
リストを作る→半分にする→さらに半分。本当に必要なものだけが残る。削ることで開発速度が上がる。
3
完璧より速さを優先する
完成度80%でリリース。残り20%はユーザーが教えてくれる。完璧を目指すとリリースできない。
4
実ユーザーに早く届ける
内部デモは学習にならない。本物のユーザーの反応だけが真実を語る。
5
測定できるものだけを作る
何を測るかを先に決める。測れない機能は後回し。データのない改善は勘に過ぎない。
6
外部サービスを最大活用する
認証・決済・メールは自分で作らない。差別化ポイントになるコア部分だけを作る。
7
モノリスから始める
必要になってから分割する。過剰設計はMVPの最大の敵。シンプルな構成が学習を速める。
8
毎週ユーザーと話す
定性フィードバックは定量と同じく重要。顧客の言葉がプロダクトを正しい方向に導く。
9
ピボットを恐れない
間違いに気づいたら素早く方向転換。失敗から学ぶのがMVPの目的。ピボットは敗北ではなく進化。
10
学習を記録する
何を仮説として・何を学んだかをドキュメントに残す。チームの集合知として蓄積する。
