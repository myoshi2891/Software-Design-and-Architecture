API-Firstとは何か？

💡 核心思想

「APIは製品である。コードを書く前に、APIという"契約"を設計し、全チームがその契約に合意してから開発をはじめる」——これがAPI-Firstの本質です。実装より先にAPIの仕様を確定させることで、フロントエンドとバックエンドが並行して開発できます。

1.1従来の開発 vs API-First

従来の「コードファースト」開発では、バックエンドが実装を完成させてからフロントエンドが統合を始めるため、認識齟齬による手戻りが頻発します。API-Firstでは仕様という共通言語を先に定義することでこの問題を根本から解決します。

1.3API-Firstが特に適しているケース

🏗️ マイクロサービス開発

複数チームが並行して異なるサービスを開発する場合、サービス間のインターフェースをAPIとして事前に定義することで、各チームが独立してデプロイできるようになります。

🌐 外部API公開

サードパーティ企業やパートナーとの連携、パブリックAPIプラットフォームの構築において、一貫した設計と充実したドキュメントが開発者体験（DX）を左右します。

📱 マルチクライアント対応

iOS・Android・Web（SPA）を同一チームまたは別々のチームが開発する場合、共通のAPIを事前に定義することでリソースの重複を防ぎます。

🏪 プラットフォームビジネス

APIをビジネスの中核に据えるエコシステム戦略や、APIマネタイズ（従量課金・サブスクリプション）を行う場合に特に有効です。

3.2ECサイト注文APIの完全YAML記述例

以下は注文管理APIのOpenAPI 3.1.0仕様の完全記述例です。各セクションの役割をコメントと合わせて確認してください。

YAML (openapi.yaml)
openapi: 3.1.0
info:
  title: ECサイト 注文管理API
  version: 2.0.0
  description: |
    ECサイトの注文管理に関するAPI仕様です。
    注文の作成・取得・キャンセルを提供します。
  contact:
    name: APIサポートチーム
    email: api-support@example.com

servers:
  - url: https://api.example.com/v2
    description: 本番環境
  - url: http://localhost:8080/v2
    description: ローカル開発環境

security:
  - BearerAuth: []   # 全エンドポイントにJWT認証を適用

paths:
  /orders:
    get:
      tags: [orders]
      summary: 注文一覧取得
      operationId: listOrders
      parameters:
        - name: status
          in: query
          schema:
            type: string
            enum: [pending, confirmed, shipped, delivered, cancelled]
        - name: page
          in: query
          schema: { type: integer, default: 1 }
      responses:
        "200":
          description: 成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/OrderListResponse"
        "401":
          $ref: "#/components/responses/Unauthorized"

    post:
      tags: [orders]
      summary: 注文作成
      operationId: createOrder
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/CreateOrderRequest"
      responses:
        "201":
          description: 注文作成成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Order"
        "400":
          $ref: "#/components/responses/BadRequest"
        "422":
          $ref: "#/components/responses/UnprocessableEntity"

components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

  schemas:
    Order:
      type: object
      required: [id, customer_id, status, total_amount, created_at]
      properties:
        id:          { type: string, example: "order_abc123" }
        customer_id: { type: string, example: "cust_12345" }
        status:
          type: string
          enum: [pending, confirmed, shipped, delivered, cancelled]
        total_amount:
          type: integer
          description: 合計金額（円）
          example: 15000
        created_at:
          type: string
          format: date-time

    ErrorResponse:
      type: object
      properties:
        error:
          type: object
          properties:
            code:    { type: string, example: "VALIDATION_ERROR" }
            message: { type: string, example: "入力値に誤りがあります" }
            details:
              type: array
              items:
                type: object
                properties:
                  field:   { type: string }
                  message: { type: string }

  responses:
    BadRequest:
      description: リクエスト不正
      content:
        application/json:
          schema: { $ref: "#/components/schemas/ErrorResponse" }
    Unauthorized:
      description: 認証エラー
      content:
        application/json:
          schema: { $ref: "#/components/schemas/ErrorResponse" }
    UnprocessableEntity:
      description: ビジネスルール違反
      content:
        application/json:
          schema: { $ref: "#/components/schemas/ErrorResponse" }

3.3OpenAPIのベストプラクティス

🔄
$ref で重複排除

同じスキーマを複数箇所で書かず、components/schemas に定義して $ref で参照する

🔖
operationId を必ず設定

SDKや型の自動生成時にメソッド名として使われる。listOrders, createOrder のように動詞+名詞で統一

📝
example を必ず記述

モックサーバーがサンプルデータとして使用する。現実的な値を記述することでテストが捗る

⚠️
エラーレスポンスを全パス定義

401/403/404/422 など、各エンドポイントで起きうる全エラーをレスポンスとして明記する

4.3URL設計ルール：良い例 vs 悪い例

✅ 良いURL設計
  • リソース名は複数形・名詞：/orders /products
  • 階層関係はパスで表現：/orders/{id}/items
  • アクションはHTTPメソッドで表現：POST /orders
  • フィルタはクエリパラメータ：/orders?status=shipped
  • バージョンはパスに：/v1/orders
  • 単語区切りはハイフン：/order-items
❌ 悪いURL設計
  • 動詞をURLに含める：/getOrders /createOrder
  • 単数形を使う：/order /product
  • 過度に深い階層：/users/{id}/orders/{id}/items/{id}/details
  • アクションをパスに：/orders/{id}/cancel
  • 拡張子を含める：/orders.json

4.4REST成熟度モデル（Richardson Maturity Model）

Richardson Maturity Model（RMM）は、RESTの原則をどれだけ採用しているかを Level 0〜3 で評価するモデルです。多くの現代APIは Level 2 を目指します。

APIのバージョニング戦略

APIは公開後も進化し続けます。既存クライアントを壊さずに新機能を追加するためのバージョニング戦略は、API設計の中でも特に重要なトピックです。

5.13つのバージョニング方式の比較

方式例メリットデメリット推奨度
URLパス GET /v1/orders 明示的・キャッシュしやすい・ブラウザで直接確認可 URLが変わる・REST的には純粋でない ◎ 推奨
HTTPヘッダー Accept: application/vnd.api.v2+json URLがクリーン・REST的に正しい クライアント実装が複雑・ブラウザ確認しにくい △ 中級向け
クエリパラメータ GET /orders?version=2 実装が簡単 キャッシュ汚染・見落としリスク ✕ 非推奨

5.2バージョンのライフサイクル

APIバージョンのライフサイクル：Alpha → Beta → GA → Deprecated → Sunset

5.3後方互換性のルール

メジャーバージョンアップ（v1→v2）を避けるため、「後方互換な変更」と「破壊的変更」を正確に区別することが重要です。

✅ 後方互換な変更（安全）
  • 新しいエンドポイントの追加
  • オプションのリクエストフィールド追加
  • レスポンスへの新しいフィールド追加
  • 新しい enum 値の追加（サーバー側）
  • エラーコードの追加
❌ 破壊的な変更（メジャーバージョン必要）
  • エンドポイントの削除・URL変更
  • 必須フィールドの追加
  • フィールドの削除・名前変更
  • レスポンス型の変更（string→int）
  • 認証方式の変更
  • HTTPメソッドの変更（GET→POST）
⚠️

廃止（Deprecated）の通知は最低6ヶ月前に

APIのバージョンを廃止する際は、DeprecationヘッダーやSunsetヘッダーをレスポンスに含め、開発者ポータルで告知を行い、移行ガイドを提供してください。突然の廃止はエコシステム全体への信頼を損ないます。

認証・認可の設計

認証（Authentication）は「あなたは誰？」を確認し、認可（Authorization）は「あなたは何ができる？」を制御します。APIにとって最も重要なセキュリティレイヤーです。

6.1主要な認証方式の比較

API認証方式の全体マップ
認証方式仕組み適したユースケース注意点
API KeyX-API-Key: {key} ヘッダーで送信内部API・シンプルなサービスキー漏洩時のリスク大。ローテーション仕組みが必要
Bearer Token（JWT）Authorization: Bearer {token}モバイルアプリ・SPA有効期限管理とリフレッシュ機構が必須
OAuth 2.0認可コード・クライアントクレデンシャルフロー外部パートナー連携・公開API実装が複雑。既存IdPの活用を検討
mTLSクライアント証明書による相互認証マイクロサービス間・金融系API証明書管理のオーバーヘッドが大きい

6.3JWTの構造と検証フロー

JWT（JSON Web Token）の構造と検証フロー
Python (FastAPI JWT検証)
import jwt
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

security = HTTPBearer()

def verify_token(credentials: HTTPAuthorizationCredentials = Depends(security)):
    # JWTトークンを検証してペイロードを返す
    token = credentials.credentials
    try:
        payload = jwt.decode(
            token,
            key=PUBLIC_KEY,           # RSA公開鍵
            algorithms=["RS256"],     # 署名アルゴリズム
            options={"verify_exp": True}  # 有効期限を検証
        )
        if "read:orders" not in payload.get("scope", "").split():
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail={"error": {"code": "AUTH_PERMISSION_DENIED",
                                  "message": "注文の読み取り権限がありません"}}
            )
        return payload
    except jwt.ExpiredSignatureError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail={"error": {"code": "AUTH_TOKEN_EXPIRED",
                              "message": "トークンの有効期限が切れています"}}
        )

7.3FastAPI実装例

Python (FastAPI エラーハンドラー)
from fastapi import FastAPI
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
import uuid

app = FastAPI()

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request, exc: RequestValidationError):
    # バリデーションエラーを統一フォーマットに変換
    details = []
    for error in exc.errors():
        details.append({
            "field": ".".join(str(loc) for loc in error["loc"][1:]),
            "message": error["msg"]
        })
    return JSONResponse(
        status_code=422,
        content={"error": {
            "code": "VALIDATION_ERROR",
            "message": "入力値に誤りがあります",
            "details": details,
            "trace_id": f"req_{uuid.uuid4().hex[:16]}"
        }}
    )

class DomainError(Exception):
    def __init__(self, code: str, message: str, status_code: int = 422):
        self.code = code
        self.message = message
        self.status_code = status_code

@app.exception_handler(DomainError)
async def domain_error_handler(request, exc: DomainError):
    return JSONResponse(
        status_code=exc.status_code,
        content={"error": {
            "code": exc.code,
            "message": exc.message,
            "trace_id": f"req_{uuid.uuid4().hex[:16]}"
        }}
    )

クライアントの種類ごとに専用のAPIレイヤーを設けます。モバイルは軽量なレスポンス、Webは豊富なデータと最適化が可能です。

10.3pytest による統合テスト実装例

Python (pytest 統合テスト)
import pytest
import httpx

BASE_URL = "http://test"

class TestOrderAPI:
    # 注文APIの統合テスト（実際のHTTPリクエストを使用）

    @pytest.fixture
    async def client(self, app):
        async with httpx.AsyncClient(app=app, base_url=BASE_URL) as c:
            yield c

    @pytest.fixture
    def auth_headers(self):
        return {"Authorization": "Bearer test_jwt_token"}

    async def test_create_order_returns_201(self, client, auth_headers):
        # 正常系：注文作成が201を返すこと
        payload = {
            "customer_id": "cust_123",
            "items": [{"product_id": "prod_001", "quantity": 2}],
            "shipping_address": {
                "postal_code": "150-0001",
                "prefecture": "東京都",
                "city": "渋谷区",
                "street": "神宮前1-1-1"
            }
        }
        response = await client.post("/v1/orders", json=payload, headers=auth_headers)
        assert response.status_code == 201
        data = response.json()
        assert data["status"] == "pending"
        assert data["customer_id"] == "cust_123"
        assert "id" in data

    async def test_get_order_returns_404_for_unknown_id(self, client, auth_headers):
        # 異常系：存在しないIDで404が返ること
        response = await client.get("/v1/orders/nonexistent", headers=auth_headers)
        assert response.status_code == 404
        error = response.json()["error"]
        assert error["code"] == "NOT_FOUND"

    async def test_create_order_returns_422_with_details(self, client, auth_headers):
        # バリデーション：詳細情報付き422が返ること
        payload = {"customer_id": "", "items": []}  # 空の値（NG）
        response = await client.post("/v1/orders", json=payload, headers=auth_headers)
        assert response.status_code == 422
        error = response.json()["error"]
        assert error["code"] == "VALIDATION_ERROR"
        assert len(error["details"]) >= 2  # 複数エラーが返る

    async def test_unauthorized_without_token(self, client):
        # 認証：トークンなしで401が返ること
        response = await client.get("/v1/orders")
        assert response.status_code == 401

API-Firstのベストプラクティス総まとめ

14.1設計フェーズのベストプラクティス

📝
コードより先に仕様を書く

実装前にOpenAPI YAMLを完成させ、仕様が承認されてから実装を開始する

👥
チームレビューを必ず実施

フロント・バック・QA・PM全員で仕様を確認し、合意形成してから着手

🎯
コンシューマー視点で設計

使いやすさ優先・実装の都合は後回し。APIは「製品」として設計する

📦
リソース中心の設計

動詞はHTTPメソッドで、名詞（リソース）をURLに。アクションをURLに混ぜない

⚠️
エラーハンドリングを先に設計

失敗パターンを正常系より先に考える。エラーコード体系を設計フェーズで確定

🏷️
バージョニング戦略を初期に決める

後から変えると全クライアントに影響。URLパスバージョニングを最初から採用

14.2実装フェーズのベストプラクティス

#カテゴリベストプラクティス理由
1仕様適合Contract Testで仕様との乖離を自動検出手動確認は漏れが発生する
2モック活用PrismでOpenAPI仕様からモックサーバーを即時起動並行開発でチームをブロックしない
3自動生成仕様からSDK・クライアントを自動生成手動実装は仕様と乖離する
4べき等性PUT/DELETEはべき等に設計する重複リクエストに安全に対処できる
5冪等キーPOSTにIdempotency-Keyヘッダーを対応ネットワーク障害時のリトライ安全性
6一貫性命名規則はsnake_caseまたはcamelCaseで全体統一クライアントの実装混乱を防ぐ
7セキュリティ全エンドポイントにOWASP API Security Top 10を適用認証バイパス・過剰データ露出を防ぐ
8可観測性全リクエストにtrace_idを付与しログに記録問題発生時の調査時間を大幅短縮

API-Firstのアンチパターン

優れたAPI設計を学ぶ最短路のひとつは失敗パターンを知ることです。以下の5つのアンチパターンは多くのプロジェクトで繰り返される典型的な失敗です。

15.15大アンチパターンとその解決策

5大アンチパターン：問題 → 解決策のマップ
#アンチパターン名症状解決策
1 Code-First（コードファースト） 実装してからAPIが後付けで決まる。ドキュメントは常に古い 実装前にOpenAPI仕様を書き、仕様承認後に実装開始。仕様レビューを必須工程に
2 RPC Style REST URLに動詞を含める設計：/getOrders, /createUser リソース名（名詞）＋HTTPメソッドで表現。URL設計ガイドラインを整備する
3 Chatty API（おしゃべりAPI） 1画面表示に10回のAPIコールが必要。N+1問題が頻発する BFFパターンでデータを集約、または ?include= で関連データを1回で取得
4 Versioning Neglect（バージョニング放棄） バージョンなしで破壊的変更。既存クライアントが突然壊れる 変更前に必ずv2を作成。最低6ヶ月の移行期間を設けてv1を廃止
5 Generic Error（汎用エラー） すべてのエラーで同じメッセージ。Internal Server Errorだけで調査不能 エラーコード体系を設計し、trace_idと詳細情報を必ず含める
