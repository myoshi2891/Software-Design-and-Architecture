01

コンポーネント指向開発とは何か？ Component-Oriented Development（COD）の基礎概念

1.1 定義：一言で理解する

コンポーネント指向開発（COD）とは、ソフトウェアシステムを 再利用可能・独立した「コンポーネント」の集合体として設計・構築する開発パラダイムです。

💡 直感的なたとえ

LEGOブロックのように、独立した部品を組み合わせてシステムを構築する考え方です。 各ブロックは単独で存在でき、違うセットでも同じブロックを再利用できます。 これがコンポーネント指向の本質です。

1.2 OOP との違い・相補的な関係

コンポーネント指向とオブジェクト指向（OOP）は対立するものではなく、異なるレベルの設計を扱います。

観点オブジェクト指向（OOP）コンポーネント指向（COD）
設計の単位クラス・インスタンスモジュール・サブシステム
主な関心事継承・ポリモーフィズム・カプセル化インターフェース契約・疎結合・再利用
スコープコードレベルの構造化アーキテクチャレベルの設計
デプロイ単一バイナリの一部独立したデプロイ単位も可能
実践での使い方コンポーネント内部を実装コンポーネント間の構造を定義
✅ 実践の鉄則

コンポーネントの内部は OOP で実装し、コンポーネント間はインターフェースで疎結合にする。両者を組み合わせることで最も効果的なアーキテクチャになります。

1.3 歴史的背景

1968年
ソフトウェア危機：NATO会議で「再利用可能な部品」の概念が初めて提唱される。複雑化するソフトウェアに「部品化」が解決策として浮上。
1992年
COM / DCOM（Microsoft）：ランタイムコンポーネントモデルの先駆けとして登場。言語に依存しないコンポーネント間通信を実現。
1998年
Enterprise JavaBeans（EJB）：サーバーサイドコンポーネントの標準化。Javaエコシステムにコンポーネント概念が普及。
2013年
Reactの登場：UIコンポーネント革命。Virtual DOM と再利用可能な UI コンポーネントの概念がフロントエンドに革命をもたらす。
2016年
Storybookの登場：コンポーネントカタログ化・ドキュメント化ツール。デザインシステムとの連携が加速。
2020年代
マイクロフロントエンド：コンポーネント指向がアーキテクチャレベルへ進化。チームの境界がコンポーネントの境界と一致する設計が主流に。

コンポーネントの設計原則 Robert C. Martin が提唱した6つの原則と高凝集・低結合

2.1 コンポーネント設計の6原則（Robert C. Martin）

Clean Architecture の著者 Robert C. Martin（Uncle Bob）が提唱した、コンポーネント設計を支える6つの原則です。凝集に関する3原則と結合に関する3原則に分類されます。

🔵
凝集の原則（何をまとめるか）

REP：再利用したいものとリリース単位を一致させる
CCP：一緒に変わるものは一緒に置く（SRP のコンポーネント版）
CRP：使わないものへの依存を作らない

🟢
結合の原則（何に依存するか）

ADP：依存グラフは DAG（有向非巡回グラフ）でなければならない
SDP：不安定→安定の方向にのみ依存する
SAP：安定＝抽象的であるべき（DIP のコンポーネント版）

2.2 高凝集・低結合の原則

コンポーネント設計における最重要概念です。高凝集はコンポーネント内部の関連性の高さ、低結合はコンポーネント間の依存の少なさを指します。

「このコンポーネントを一言で説明できますか？」と自問してください。 説明に「〜かつ〜」や「〜と〜」が入ったら、分割のサインです。

2.3 インターフェース契約（Contract）の設計

コンポーネントのインターフェースは「契約」です。変更しにくく、明確に定義する必要があります。 契約には4つの要素があります。

📥
入力（Props / パラメータ）

コンポーネントが受け取るデータ。型・必須/任意・デフォルト値を明示します。

📤
出力（Events / 戻り値）

コンポーネントが外部に返すイベント・コールバック・戻り値。

🎰
スロット / Children

コンポーネント内部に外部からコンテンツを注入できる差し込み口。

⚡
副作用の宣言

API呼び出し・状態更新など外部に影響する処理を明示的に宣言する。

4.2 Props Down / Events Up（基本パターン）

最もシンプルで追跡しやすいパターンです。データは上から下へ（Props）、イベントは下から上へ（callback）という一方向フローを維持します。

🔄 図4-2：Props Down / Events Up シーケンス
sequenceDiagram
    participant PP as 親 ProductPage
    participant PC as 子 ProductCard
    participant AB as 孫 AddToCartButton
    Note over PP,AB: ⬇️ Props Down（データを下に流す）
    PP->>PC: product={id, name, price}
    PC->>AB: productId={id}, onAdd={handler}
    Note over PP,AB: ⬆️ Events Up（イベントを上に伝える）
    AB-->>PC: onAdd(productId, quantity) を呼ぶ
    PC-->>PP: onAddToCart(product) を呼ぶ
    PP->>PP: カートに商品を追加する処理
✅ ベストプラクティス

2〜3階層以内であれば Props Down / Events Up を使いましょう。 シンプルでデータフローが追跡しやすく、デバッグが容易です。 それ以上の深さになったら Context / Store を検討してください。

05

UIコンポーネント設計（フロントエンド） React / Vue における実装ベストプラクティスと Custom Hooks

5.1 React コンポーネント設計の6原則

📌
単一責任

1コンポーネント = 1つの役割。肥大化したら迷わず分割する。

🏷️
Props を型定義

TypeScript で厳密に型付け。必須/任意を明示し、ドキュメント代わりにする。

🎯
デフォルト値を設定

オプショナルな Props には適切なデフォルト値を与え、呼び出し側の負担を減らす。

⚡
Pure に保つ

同じ Props → 同じ出力。副作用は Custom Hooks に分離する。

🔀
継承より合成

コンポーネントの継承は避け、children / render props / Slot で合成する。

🧹
状態を最小化

Props で表現できるものは state にしない。必要な状態だけを持つ。

5.2 Button コンポーネント実装例（Atom）React + TypeScript

コンポーネントのライフサイクル管理 Mounting / Updating / Unmounting の各フェーズと実装パターン

7.1 フロントエンドコンポーネントのライフサイクル

🔄 図7-1：コンポーネントライフサイクル（React / Vue）
stateDiagram-v2
    [*] --> Mounting : コンポーネント生成
    state Mounting {
        [*] --> InitState : state 初期化
        InitState --> FirstRender : 初回レンダリング
        FirstRender --> DidMount : DOM に挿入
        DidMount --> [*] : API呼び出し・イベント登録
    }
    Mounting --> Updating : Props / State 変更
    state Updating {
        [*] --> ShouldUpdate : 更新が必要か判断
        ShouldUpdate --> Rerender : Yes → 再描画
        ShouldUpdate --> Skip : No → スキップ（最適化）
        Rerender --> DidUpdate : 更新完了
        DidUpdate --> [*]

    }

    Updating --> Unmounting : コンポーネント削除
    state Unmounting {
        [*] --> Cleanup : クリーンアップ処理
        Cleanup --> [*] : イベント解除・タイマーキャンセル・リクエスト中断
    }
    Unmounting --> [*]
🚀
Mounting フェーズ

コンポーネントが初めて DOM に挿入されるとき。API 呼び出し・イベントリスナー登録・タイマー開始などの初期化処理を行います。

🔄
Updating フェーズ

Props や State が変更されたとき。不要な再レンダリングを防ぐ最適化（useMemo/useCallback/React.memo）が重要です。

🧹
Unmounting フェーズ

コンポーネントが削除されるとき。クリーンアップを忘れるとメモリリークの原因に。イベント解除・タイマーキャンセル・リクエスト中断が必須です。

TypeScript / React コンポーネントのライフサイクル管理
⚠️ 最も多い落とし穴：クリーンアップ忘れ

useEffect の return 関数（クリーンアップ）を忘れると、アンマウント後も API リクエストが継続し、存在しないコンポーネントの state を更新しようとして「Warning: Can't perform a React state update on an unmounted component」エラーが発生します。必ず AbortController と clearInterval でクリーンアップしてください。

    単一責任：1コンポーネント = 1つの明確な役割。「〜かつ〜」があれば分割。
  • ✅
    Props を最小限に：必要なデータだけを受け取る。不要な Props は依存を増やす。
  • ✅
    TypeScript で型定義：Props / Events を厳密に型付けしてインターフェース契約を明文化。
  • ✅
    デフォルト値を設定：オプショナルな Props には適切なデフォルト値を与える。
  • ✅
    副作用を分離：API 呼び出しは Custom Hooks / サービス層に切り出す。
  • ✅
    テストを書く：ユニット・統合・ビジュアルテストを整備。CI で自動実行。
  • ✅
    アクセシビリティ：aria 属性・キーボード操作・カラーコントラストを考慮。
  • ✅
    Storybook でカタログ化：全状態をストーリーとして記録。チームの共通認識に。
  • ✅
    クリーンアップを忘れずに：useEffect の return でイベント解除・タイマーキャンセル・リクエスト中断。
  • ✅
    ErrorBoundary でラップ：コンポーネントのエラーが全体に波及しないよう隔離する。

14.2 コンポーネント指向 成熟度モデル

Lv.0
初期
モノリシックなビュー
コンポーネント分割なし。ページ単位の大きな実装。変更のたびに全体に影響が波及する。
Lv.1
基礎
基本的なコンポーネント化
再利用されるパーツ（Button / Input など）を切り出す。コンポーネント化の概念を理解している。
Lv.2
体系化
アトミックデザインの導入
Atoms / Molecules / Organisms の階層でシステマティックに粒度を管理できる。
Lv.3
標準化
デザインシステムの確立
デザイントークン・共有コンポーネントライブラリ・Storybook でカタログ化。チーム全体で一貫性を保証。
Lv.4
分離
Container / Presentational の完全分離
ロジックと UI の完全分離。Custom Hooks による再利用・テストが容易な設計が実現できている。
Lv.5
最適化
マイクロフロントエンド
コンポーネントが独立したチームの境界と一致。独立デプロイ・完全な疎結合・チームの自律性が最大化。

14.4 ライフサイクル別ベストプラクティス

フェーズベストプラクティス理由
設計最も小さい粒度から設計（Atoms から）再利用性と組み合わせやすさが向上する
実装Pure コンポーネントを目指すテストしやすく予測可能な動作を保証
状態管理状態は最も近い親コンポーネントに置く不要なグローバル状態を避ける
通信Props Down / Events Up を基本にするデータフローが追跡しやすい
依存インターフェースに依存（具体実装に依存しない）テストと差し替えが容易になる
テストユーザー操作ベースのテストを書く実装ではなく振る舞いを検証する
ドキュメントStorybook で全状態を記録するチームの共通認識と品質保証
リリースセマンティックバージョニングを使う破壊的変更を明確にする
