01

BDDとは何か？

Behavior-Driven Development（振る舞い駆動開発）は Dan North が 2006 年に提唱した開発手法です。TDD を発展させ、ビジネス関係者・開発者・テスターが共通言語でシステムの振る舞いを先に定義し、それを実行可能な仕様として自動テストに落とし込むアプローチです。

💡
核心思想

「テストは技術者のためだけのものではない。ビジネス側と技術側が同じ言葉でシステムの期待する振る舞いを記述し、その仕様そのものが自動テストとして動き続ける」

1.1 BDDが解決する4つの問題
❌ 導入前：要件の認識齟齬
PO・開発者・QA が同じ文書を読んでも異なる解釈をする。認識合わせのコストが膨大になる。
✅ 導入後：共通言語で合意
Gherkin シナリオが「唯一の真実」として機能。全員が同じ具体例に基づいて議論できる。
❌ 導入前：仕様書が陳腐化
Word の要件定義書はコードと乖離し続ける。「誰も読まないドキュメント問題」が慢性化。
✅ 導入後：生きた仕様書
シナリオがそのまま自動テストとして動き続ける。コードとドキュメントが常に一致する。
1.2 TDD・BDD・ATDDの位置づけ

3 つの手法は互いを補完する入れ子構造になっています。BDD は ATDD の実践手法であり、TDD を補完する外側のループとして機能します。

🔵
ATDD（最外層）
受け入れテスト駆動開発。顧客視点で受け入れ基準を定義する最外側のループ
🟢
BDD（中間層）
Gherkin 記法でシナリオを記述。ビジネスと技術の橋渡しをする
🔴
TDD（最内層）
コードレベルのユニットテスト。開発者中心の最も細かいループ
1.3 BDDが特に効果的な状況
✅ 適したチーム構成
  • ●PO・BA・開発者・QA が混在するチーム
  • ●ビジネス側が仕様に積極的に関与する
  • ●認識齟齬・手戻りが頻発している
  • ●アジャイル・スクラムを実践している
✅ 適したプロジェクト特性
  • ●複雑なビジネスルールが多数ある
  • ●受け入れ基準が曖昧になりやすい
  • ●長期保守される基幹システム
  • ●リグレッションが頻発している
02

BDDの基本：Given-When-Then構文

Given-When-Then（GWT）は BDD シナリオを記述するための構造化された構文です。「前提条件・操作・期待結果」の 3 ステップでシステムの振る舞いを誰でも読める形で表現します。

2.1 各キーワードの役割
Given
前提条件（Context）
テスト開始時のシステム状態。「〜の状態において」「〜である場合」を記述。例：顧客がログインしている
When
操作・イベント（Action）
ユーザーまたはシステムのアクション。「〜したとき」「〜が発生したとき」を記述。例：商品をカートに追加する
Then
期待される結果（Outcome）
システムが示すべき振る舞い。「〜になるはずである」「〜が表示されるはずである」を記述。例：合計金額が表示される
2.2 And / But キーワード

And と But は前のステップと同種のステップを継続するために使います。

📖
記述例

Given 顧客の口座残高が 10,000円 である
And 本人確認が完了している
When 顧客が 3,000円 を引き出す
Then 口座残高は 7,000円 になる
And 取引明細に「出金 3,000円」が記録される

2.3 良いGWTと悪いGWTの比較
✅ 良い GWT

Given 顧客「山田太郎」がログインしている
When 商品「Tシャツ」を 1 点カートに追加する
Then カートに 1 点の商品が入っている
And カートの合計金額は 1,000円 である

  • ✓ 具体的な名前と数値
  • ✓ 1シナリオ1ふるまい
  • ✓ ビジネス語彙のみ使用
❌ 悪い GWT

Given システムが正常な状態
When ボタンをクリックする
Then データが保存される

  • ✗ 「正常な状態」が曖昧
  • ✗ どのボタンか不明
  • ✗ 検証基準がない
2.4 ユーザーストーリーとGWTの関係

ユーザーストーリーは「何を・なぜ」を表現し、BDD シナリオはそれを「具体的な例」に変換します。1 ストーリーから正常系・異常系の複数シナリオが生まれます。

Gherkin記法の完全解説

Gherkin は BDD シナリオを記述するための構造化された自然言語記法です。英語・日本語など多言語に対応し、Cucumber をはじめ多くの BDD フレームワークが採用しています。

3.1 全キーワード体系
キーワード用途使用場所補足
Featureテストする機能の説明ファイル先頭（1つだけ）ユーザーストーリーを記述することが多い
Background全シナリオ共通の前提条件Feature 直後Given・And・But ステップのみ使用可
Scenario1 つの具体的なテストケースFeature 内明確で具体的なタイトルをつける
Scenario Outlineパラメータ化されたシナリオFeature 内Examples テーブルと必ずセットで使う
Given / When / Then前提条件 / 操作 / 期待結果Scenario 内それぞれ独立した役割を持つ
And / But前のステップと同種のステップを継続Scenario 内Given-And-And の形でも使用可
ExamplesScenario Outline のパラメータテーブルOutline 直後複数の Examples ブロックも記述可能
@タグシナリオの分類・フィルタリングFeature/Scenario 前例：@smoke @regression @wip @api
DocString複数行テキスト（3 つのダブルクォート）ステップ直後（インデント）JSON・SQL・XML 等の長いデータに使用
| テーブル |DataTable：表形式データステップ直後（インデント）複数のパラメータを整理して渡す
3.2 Featureファイルの完全記述例
features/shopping_cart.feature
Gherkin
@shopping @cart
Feature: ショッピングカートの操作
  登録済みの顧客として
  カートに商品を追加・削除したい
  まとめて購入を確定できるから

  Background:
    Given 以下の商品がカタログに登録されている
      | 商品ID   | 商品名   | 価格 | 在庫数 |
      | prod_001 | Tシャツ  | 1000 | 10     |
      | prod_002 | ジーンズ | 5000 | 3      |
      | prod_003 | キャップ | 2000 | 0      |
    And 顧客「山田太郎（cust_001）」がログインしている

  @smoke
  Scenario: 商品をカートに追加する
    Given カートが空の状態である
    When 商品「Tシャツ」を 1 点カートに追加する
    Then カートには 1 点の商品が入っている
    And カートの合計金額は 1,000円 である

  @negative
  Scenario: 在庫切れの商品はカートに追加できない
    Given カートが空の状態である
    When 商品「キャップ」をカートに追加しようとする
    Then 「在庫切れのため追加できません」というエラーが表示される
    And カートの中身は変わらない

  @parameterized
  Scenario Outline: 異なる数量で商品をカートに追加する
    Given カートが空の状態である
    When 商品「Tシャツ」を <数量> 点カートに追加する
    Then カートの合計金額は <合計金額> 円である
    Examples:
      | 数量 | 合計金額 |
      | 1    | 1000     |
      | 2    | 2000     |
      | 5    | 5000     |

  @api
  Scenario: APIを通じて注文を作成する
    Given カートに商品「Tシャツ」が 1 点入っている
    When 以下のJSONで注文を送信する（DocString）
      """json
      {
        "shipping_address": { "postal_code": "150-0001", "prefecture": "東京都" },
        "payment_method": "credit_card"
      }
      """
    Then レスポンスステータスは 201 である
    And レスポンスに "order_id" フィールドが含まれている
3.3 タグの活用戦略
@smoke
スモークテスト
最小限の動作確認。PR 時に高速実行（5 分以内）。最重要シナリオに付与する。
@regression
リグレッション
マージ前の全機能確認。CI/CD パイプラインで実行する全シナリオ対象。
@wip
開発中（WIP）
作業中シナリオ。CI では除外。完成したら削除する一時的タグ。
@negative
異常系テスト
エラー・例外シナリオのグルーピング。@smoke とは分離して管理する。
@api
APIテスト
HTTP レベルのテストシナリオ。API サーバーが起動している環境で実行。
@e2e
E2Eテスト
ブラウザ操作を伴うフルスタックテスト。本番近似環境でのみ実行。
04

BDDの開発フロー

BDD は単なるテスト技法ではなく、要件定義から実装・ドキュメント化までをカバーする開発プロセスです。「発見→定式化→自動化→検証→生きた仕様書」の 5 ステップで進みます。

4.1 BDD全体開発サイクル
  1. 1
    Discovery（発見）— Three Amigos ミーティング

    PO・開発者・QA が集まり、機能の振る舞いを議論。「具体的な例」を出し合うことで認識のズレを発見する。所要時間：30〜60 分/ストーリー

  2. 2
    Formulation（定式化）— Gherkin 記述

    議論から生まれた具体例を Gherkin 記法で記述。あいまいさをなくし、全員が「Yes, that's right」と言える仕様書を作る。

  3. 3
    Automation（自動化）— ステップ定義

    Gherkin シナリオをステップコードにバインドして FAIL する自動テストを作る。「レッド」状態から開発を始める。

  4. 4
    Validate（検証）— 実装とテスト通過

    シナリオをパスする実装を行い「グリーン」にする。ビジネス側が実行結果を確認し受け入れる。

  5. 5
    Living Documentation（生きた仕様書）

    シナリオは常に実行可能な最新の仕様書として機能し続ける。コードとドキュメントの乖離が構造的に発生しない。

4.2 Three Amigos ミーティング
💬
Three Amigos の進め方（30〜60 分）

① PO がビジネスルールと目的を説明 → ② QA がエッジケース・異常系を提案 → ③ 開発者が技術的制約を共有 → ④ 3 者合意の Gherkin シナリオを作成 → ⑤ Feature ファイルをリポジトリにコミット

package steps;

import io.cucumber.java.ja.*;
import io.cucumber.java.*;
import static org.assertj.core.api.Assertions.*;

public class ShoppingCartSteps {

    private ShoppingCart cart;
    private ProductCatalog catalog;
    private Exception lastException;

    @Before
    public void setUp() {
        catalog = new InMemoryProductCatalog();
        cart = new ShoppingCart(catalog);
    }

    @After
    public void tearDown() { cart = null; }

    // ─── Given ステップ ───
    @Given("カートが空の状態である")
    public void カートが空の状態である() {
        assertThat(cart.isEmpty()).isTrue();
    }

    @Given("顧客{string}がログインしている")
    public void 顧客がログインしている(String customerName) {
        AuthContext.login(customerName);
    }

    // ─── When ステップ ───
    @When("商品{string}を {int} 点カートに追加する")
    public void 商品をカートに追加する(String productName, int quantity) {
        try {
            Product product = catalog.findByName(productName);
            cart.addItem(product.getId(), quantity);
        } catch (Exception e) {
            lastException = e;
        }
    }

    // ─── Then ステップ ───
    @Then("カートには {int} 点の商品が入っている")
    public void カートには点の商品が入っている(int expectedCount) {
        assertThat(cart.getTotalQuantity()).isEqualTo(expectedCount);
    }

    @Then("カートの合計金額は {int}円 である")
    public void カートの合計金額は円である(int expectedTotal) {
        assertThat(cart.getTotal()).isEqualTo(expectedTotal);
    }

    @Then("{string}というエラーが表示される")
    public void エラーが表示される(String expectedMessage) {
        assertThat(lastException).isNotNull();
        assertThat(lastException.getMessage()).contains(expectedMessage);
    }
}

import pytest
from dataclasses import dataclass, field
from typing import Optional, Any
import httpx
from src.domain.cart import ShoppingCart
from src.infrastructure.in_memory_catalog import InMemoryProductCatalog


@dataclass
class ScenarioContext:
    """ステップ間で状態を共有するコンテキストクラス"""
    last_error:    Optional[Exception] = None
    last_response: Optional[httpx.Response] = None
    data:          dict = field(default_factory=dict)

    def set(self, key: str, value: Any) -> None:
        self.data[key] = value

    def get(self, key: str, default: Any = None) -> Any:
        return self.data.get(key, default)

    def reset(self) -> None:
        self.last_error = None
        self.last_response = None
        self.data.clear()


@pytest.fixture
def product_catalog():
    return InMemoryProductCatalog()


@pytest.fixture
def shopping_cart(product_catalog):
    return ShoppingCart(catalog=product_catalog)


@pytest.fixture
def context() -> ScenarioContext:
    """各シナリオ用コンテキスト（function スコープ）"""
    ctx = ScenarioContext()
    yield ctx
    ctx.reset()  # テスト後に自動リセット


@pytest.fixture(scope="session")
def db_engine():
    """DB エンジン（セッション全体で 1 回のみ作成）"""
    from sqlalchemy import create_engine
    from src.infrastructure.db import Base
    engine = create_engine("sqlite:///:memory:")
    Base.metadata.create_all(engine)
    yield engine
    engine.dispose()


@pytest.fixture
def db_session(db_engine):
    """DB セッション（各テストごとにロールバック）"""
    from sqlalchemy.orm import sessionmaker
    Session = sessionmaker(bind=db_engine)
    session = Session()
    yield session
    session.rollback()  # テスト後ロールバックでクリーンな状態を保証
    session.close()

import pytest
from pytest_bdd import given, when, then, parsers
from src.domain.cart import ShoppingCart, InsufficientStockError
from decimal import Decimal


# ─────────── Given ステップ ───────────

@given("カートが空の状態である")
def cart_is_empty(shopping_cart):
    assert shopping_cart.is_empty, "カートは空でなければなりません"


@given(parsers.parse("カートに商品「{product_name}」が{quantity:d}点入っている"))
def cart_has_items(product_name, quantity, shopping_cart, product_catalog):
    product = product_catalog.find_by_name(product_name)
    shopping_cart.add_item(product.id, quantity)


@given("カートに以下の商品が入っている")
def cart_has_multiple_items(shopping_cart, product_catalog, datatable):
    for row in datatable:
        product = product_catalog.find_by_name(row["商品名"])
        shopping_cart.add_item(product.id, int(row["数量"]))


# ─────────── When ステップ ───────────

@when(parsers.parse("商品「{product_name}」を{quantity:d}点カートに追加する"))
def add_item_to_cart(product_name, quantity, shopping_cart, product_catalog, context):
    context.last_error = None
    try:
        product = product_catalog.find_by_name(product_name)
        shopping_cart.add_item(product.id, quantity)
    except InsufficientStockError as e:
        context.last_error = e


@when(parsers.parse("商品「{product_name}」をカートに追加しようとする"))
def try_add_out_of_stock(product_name, shopping_cart, product_catalog, context):
    context.last_error = None
    try:
        product = product_catalog.find_by_name(product_name)
        shopping_cart.add_item(product.id, 1)
    except InsufficientStockError as e:
        context.last_error = e


@when(parsers.parse("カートから「{product_name}」を削除する"))
def remove_item_from_cart(product_name, shopping_cart, product_catalog):
    product = product_catalog.find_by_name(product_name)
    shopping_cart.remove_item(product.id)


# ─────────── Then ステップ ───────────

@then(parsers.parse("カートには{expected_count:d}点の商品が入っている"))
def cart_has_count(expected_count, shopping_cart):
    assert shopping_cart.total_quantity == expected_count, (
        f"期待: {expected_count}点, 実際: {shopping_cart.total_quantity}点"
    )


@then(parsers.parse("カートの合計金額は{expected_total:d}円である"))
def cart_total_is(expected_total, shopping_cart):
    assert shopping_cart.total == Decimal(str(expected_total)), (
        f"期待: {expected_total}円, 実際: {shopping_cart.total}円"
    )


@then(parsers.parse("「{expected_message}」というエラーが表示される"))
def error_message_displayed(expected_message, context):
    assert context.last_error is not None, "エラーが発生しませんでした"
    assert expected_message in str(context.last_error), (

ステップ定義のベストプラクティス

8.1 良いステップ定義の設計原則
✅ 良いステップ定義
  • ✓再利用可能な汎用ステップを書く
  • ✓1ステップ = 1つの明確な操作
  • ✓ビジネス語彙を使った命名
  • ✓parsers.parse でパラメータ対応
  • ✓例外もキャッチして context に保存
  • ✓アサーションは Then ステップのみ
❌ 避けるべき書き方
  • ✗UI 操作の詳細をステップに直接書く
  • ✗1ステップで複数のことを検証
  • ✗技術的詳細（URL・セレクター）を露出
  • ✗ステップ間でグローバル変数を使う
  • ✗Given 内でアサーションを行う
  • ✗重複ステップを複数ファイルに定義

9.1 フィクスチャのスコープ選択指針
スコープ生存期間推奨用途BDD での使用
sessionセッション全体で 1 回DB エンジン・ブラウザ起動・重い初期化⚠️ 限定的に使用
moduleファイル単位モジュール共通の設定オブジェクト⚠️ 限定的に使用
function（デフォルト）各テスト関数ごとほぼすべてのフィクスチャ✅ BDD での標準
classクラス単位クラス内テストで状態共有が必要な場合⚠️ 稀に使用
💡
BDD のベストプラクティス

BDD シナリオには原則として function スコープを使用します。各シナリオが独立して実行できることが最重要であり、前のシナリオの状態が次のシナリオに漏れ出ることを防ぎます。session スコープは DB 接続など「重い初期化」に限定してください。

9.2 DB トランザクション管理パターン
Python
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from src.infrastructure.db import Base


@pytest.fixture(scope="session")
def db_engine():
    """セッション全体で 1 回のみ作成（重いため）"""
    engine = create_engine("sqlite:///:memory:", echo=False)
    Base.metadata.create_all(engine)
    yield engine
    engine.dispose()


@pytest.fixture
def db_session(db_engine):
    """
    各テストごとにネストトランザクションを作成し、
    テスト後に必ずロールバックして DB をクリーンに保つ
    """
    connection = db_engine.connect()
    transaction = connection.begin()
    Session = sessionmaker(bind=connection)
    session = Session()

    yield session

    session.close()
    transaction.rollback()  # テスト後に必ずロールバック
    connection.close()


@pytest.fixture
def api_client(app, db_session):
    """FastAPI テストクライアント。db_session を差し込む。"""
    from fastapi.testclient import TestClient
    app.dependency_overrides[get_db] = lambda: db_session
    with TestClient(app) as client:
        yield client
    app.dependency_overrides.clear()

BDD と TDD の二重ループ

BDD と TDD は対立するものではなく、外側（BDD）と内側（TDD）の二重ループとして連携します。外側の BDD ループが「何を作るか」を規定し、内側の TDD ループが「どう作るか」を駆動します。

10.1 二重ループの実践フロー
  1. 1
    BDD RED — Gherkin シナリオを書く

    新機能の Gherkin シナリオを作成。ステップ定義がないため「PENDING」か「FAIL」になる

  2. 2
    TDD RED — ユニットテストを書く

    シナリオを実現するためのユースケース・ドメインモデルのユニットテストを書く（実装なし）

  3. 3
    TDD GREEN — 最小実装で PASS

    ユニットテストをパスする最小限の実装コードを書く。過剰実装しない

  4. 4
    TDD REFACTOR — コードを整理

    テストを壊さずにコードを改善。2〜4 を繰り返してドメインモデルを育てる

  5. 5
    BDD GREEN — シナリオが PASS

    ステップ定義を完成させてシナリオを実行。すべて GREEN になったら次のシナリオへ

  6. 6
    BDD REFACTOR — シナリオを整理

    重複シナリオの統合・Background の整理・タグの見直しを行う

📌
重要な原則

BDD シナリオが「FAIL（赤）」の間は、TDD ループで着実に実装を積み重ねます。BDD シナリオが「PASS（緑）」になるまで TDD ループを繰り返すのが二重ループの本質です。「BDD を後から書く」アプローチは BDD ではありません。

17.1 シナリオ設計ベストプラクティス一覧
カテゴリベストプラクティス理由
記述スタイル宣言的に書く（「何を」のみ）UI 変更の影響を受けない
粒度1 シナリオ = 1 ビジネスルール失敗原因を特定しやすい
命名ビジネス語彙で具体的に書く非エンジニアにも理解できる
データ具体的な数値・名前を使う曖昧さをなくし期待値を明確に
独立性Background に最小限の前提のみシナリオ間の依存を排除
タグ@smoke/@regression/@wip で分類必要なシナリオだけを幕別実行
シナリオ数Feature あたり 5〜10 個が目安多すぎると保守困難
パラメータ化類似シナリオは Scenario Outline で集約重複を排除し保守性向上

BDD のアンチパターン

18.1 主要アンチパターン一覧
❌ 実装詳細の露出
「id=submit-btn のボタンをクリック」「POST /api/v1/orders を送信」など技術的詳細をステップに書く。UI 変更のたびにシナリオが壊れる。
✅ 解決：「注文を確定する」のようにビジネス語彙で記述する
❌ God Scenario（神シナリオ）
ログイン→検索→カート→決済→メール→在庫確認を 1 シナリオで検証。30 ステップ超のモンスターシナリオ。デバッグ不能。
✅ 解決：1 シナリオ 1 振る舞いに分割。ステップ数 5〜10 個を目安に
❌ シナリオ間の依存
「前のシナリオで作った注文を参照する」のように実行順序に依存。並列実行や順序変更で壊れる。
✅ 解決：Background と Given で毎回データをセットアップする
❌ 技術者だけが書くシナリオ
PO や QA が参加せず開発者だけが Feature を書く。ビジネス要件からずれた「コードのテスト」になってしまう。
✅ 解決：Three Amigos を実践。PO・開発者・QA の 3 者で作成する
❌ 過剰なシナリオ数
すべての入力組み合わせをシナリオ化。類似シナリオが何十個も存在し保守コストが爆発する。
✅ 解決：Scenario Outline で集約。網羅的テストはユニットテストに委譲
❌ 失敗シナリオの放置
「後で直す」と失敗シナリオをコミットし続ける。Broken Window 効果でチーム全体のテスト品質が低下する。
✅ 解決：失敗シナリオは即座に修正。一時的に @skip を使いチケット起票
