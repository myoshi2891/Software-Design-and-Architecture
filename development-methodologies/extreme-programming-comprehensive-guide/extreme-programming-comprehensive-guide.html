Section 01

XPとは何か

Extreme Programming の定義・背景・全体像

一言で言うと：「変化を受け入れ、顧客価値を最速で届けるために、最も効果的な開発プラクティスを組み合わせた方法論」

Extreme Programming（XP）は Kent Beck が1990年代後半に提唱したアジャイルソフトウェア開発の方法論です。 1999年の著書「Extreme Programming Explained」によって広く知られるようになりました。 XPは「良いプラクティスを極限まで実践すれば、品質・速度・適応力のすべてを同時に高められる」という思想に基づいています。

XPの5つの価値（Values）

すべてのプラクティスは5つの価値から導かれる

価値を理解せずにプラクティスだけを実践しても、本来の効果は得られません。まず価値を理解することが最初のステップです。

💬 コミュニケーション
チーム全員が同じ情報を持つ。直接対話を最優先し、問題を一人で抱え込まない。ペアプロ・スタンドアップで実現。
✂️ シンプルさ
今必要なことだけを行う。過剰設計・過剰実装をせず、YAGNIを守る。シンプルな設計・リファクタリングで実現。
🔄 フィードバック
早く・頻繁に・積極的にフィードバックを求め、活かす。テスト・小さなリリース・CI で実現。
💪 勇気
悪いコードを直す・設計を変える・真実を伝える勇気を持つ。リファクタリング・技術的負債の解消で実現。
🤝 尊重
全チームメンバーを尊重する。貢献と努力を認め合い、失敗を学習機会とする。コレクティブオーナーシップ・ペアプロで実現。

Section 04

プラクティス① テスト駆動開発（TDD）

コードを書く前にテストを書く革新的アプローチ

XPの最重要プラクティス：TDDはXPの根幹です。「動くソフトウェア」を保証し、リファクタリングを安全にし、設計品質を高めます。

Red-Green-Refactor サイクル

flowchart TD START(["新機能を実装する"]) RED["🔴 RED フェーズ\n失敗するテストを書く\nまだ実装コードは存在しない\nテストは必ず失敗する"] GREEN["🟢 GREEN フェーズ\n最小限の実装コードを書く\nテストを通すだけの最小限\n美しさより動作を優先"] REFACTOR["🔵 REFACTOR フェーズ\nコードを整理・改善する\nテストを壊さない範囲で\n重複排除・命名改善"] CHECK{"全機能実装完了？"} DONE(["実装完了"]) START --> RED --> GREEN --> REFACTOR --> CHECK CHECK -->|No| RED CHECK -->|Yes| DONE

良いテストのFIRST原則

F — Fast（高速）
ミリ秒単位で実行できる。DBや外部APIに依存しない。いつでも気軽に実行できる。
I — Independent（独立）
テスト間に依存関係がない。任意の順序で実行できる。単独でも全体でも動く。
R — Repeatable（再現可能）
何度実行しても同じ結果。環境に依存しない。時刻・乱数は注入して制御。
S — Self-validating（自己検証）
Pass/Failが自動判定される。目視確認が不要。明確なアサーションがある。
T — Timely（タイムリー）
本番コードの直前に書く。後回しにしない。TDDならコードの前に書く。

TDD実装例（Python）— Red-Green-Refactor

# ─── Step 1：RED フェーズ ─── まずテストを書く ───
import pytest
from order import Order  # まだ存在しない！

class TestOrder:
    def test_新規注文の合計金額は0円(self):
        order = Order()
        assert order.total == 0

    def test_商品追加後に合計金額が更新される(self):
        order = Order()
        order.add_item("Tシャツ", price=1000, quantity=2)
        assert order.total == 2000

    def test_数量0の商品は追加できない(self):
        order = Order()
        with pytest.raises(ValueError, match="数量は1以上"):
            order.add_item("Tシャツ", price=1000, quantity=0)

# → この時点でテストを実行すると全てFAIL ✅（RED）


# ─── Step 2：GREEN フェーズ ─── 最小実装を書く ───
class Order:
    def __init__(self):
        self._items = []

    def add_item(self, name: str, price: int, quantity: int) -> None:
        if quantity <= 0:
            raise ValueError("数量は1以上でなければなりません")
        self._items.append({"name": name, "price": price, "quantity": quantity})

    @property
    def total(self) -> int:
        return sum(item["price"] * item["quantity"] for item in self._items)

# → 全テストがPASS ✅（GREEN）


# ─── Step 3：REFACTOR フェーズ ─── コードを整理 ───
from dataclasses import dataclass

@dataclass(frozen=True)
class OrderItem:
    name: str
    price: int
    quantity: int

    def __post_init__(self):
        if self.quantity <= 0:
            raise ValueError("数量は1以上でなければなりません")

    @property
    def subtotal(self) -> int:
        return self.price * self.quantity

class Order:
    def __init__(self):
        self._items: list[OrderItem] = []

    def add_item(self, name: str, price: int, quantity: int) -> None:
        self._items.append(OrderItem(name=name, price=price, quantity=quantity))

    @property
    def total(self) -> int:
        return sum(item.subtotal for item in self._items)

# → リファクタリング後もテストが全てPASS ✅（REFACTOR）

TDDベストプラクティス

項目推奨理由
テスト名日本語や自然言語で意図を明確に仕様書として読めるようにする

XP流CI 10のルール

#ルール理由
1単一のメインブランチ（長命ブランチを作らない）統合コストを最小化
2ビルドを自動化する（コマンド1つで再現可能）手作業によるミスを排除
3テストを自動化する（コマンド1つで全実行）継続的な品質保証
4全員が毎日mainブランチに統合する統合の問題を小さく保つ
5ビルドは10分以内遅いCIは誰も待たない
6ビルド失敗は最優先で修正壊れたビルドを放置しない
7テスト失敗はコミットしない赤いビルドを積み上げない
8結果を全員に可視化誰もが状態を知っている
9フィーチャーブランチは最小化（1日以内）長命ブランチは統合コストを増やす
10Trunk-Based Developmentを目指す常にデプロイ可能な状態

GitHub Actions CI設定例

# .github/workflows/ci.yml
# XP流：プッシュのたびに自動実行されるCIパイプライン

name: XP Continuous Integration

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  fast-checks:
    name: Lint & Unit Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - name: Install dependencies
        run: pip install -r requirements-dev.txt
      - name: Lint check (ruff)
        run: ruff check .
      - name: Type check (mypy)
        run: mypy src/
      - name: Unit tests with coverage
        run: |
          pytest tests/unit/ \
            --cov=src \
            --cov-fail-under=90 \
            -v --tb=short -n auto

  slow-checks:
    name: Integration & E2E Tests
    runs-on: ubuntu-latest
    needs: fast-checks
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_DB: test_db
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
    steps:
      - uses: actions/checkout@v4
      - name: Integration tests
        env:
          DATABASE_URL: postgresql://test:test@localhost/test_db
        run: pytest tests/integration/ -v
      - name: Security scan
        run: pip-audit

  notify-failure:
    name: Notify on Failure
    runs-on: ubuntu-latest
    needs: [fast-checks, slow-checks]
    if: failure()
    steps:
      - name: Slack notification
        uses: slackapi/slack-github-action@v1
        with:
          payload: '{"text":"CIビルドが失敗しました！即座に修正してください"}'
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}

Section 07

プラクティス④ リファクタリング

動作を変えずに内部のコード構造を改善する

ボーイスカウトルール：「来たときよりキャンプ場をきれいにして帰りなさい」— コードに触れたら少し良くして帰る。

主要なリファクタリングパターン

カテゴリパターン名目的
メソッドの整理メソッドの抽出（Extract Method）長いメソッドを意味のある単位に分割
メソッドの整理メソッドの移動（Move Method）正しいクラスにロジックを移動
命名の改善変数名の変更（Rename Variable）意図が明確な名前に変える
命名の改善メソッド名の変更（Rename Method）何をするかがわかる名前に
クラスの整理クラスの抽出（Extract Class）責任が多すぎるクラスを分割
条件式の改善条件式の分解（Decompose Conditional）複雑なif-elseを読みやすくする
条件式の改善ガード節による早期リターンネストを浅くし意図を明確に
重複の排除DRY原則の適用同じロジックを1か所にまとめる

リファクタリングのタイミング

新機能実装前
コードを理解しながら整理する。変更しやすい状態を作ってから機能追加。
TDDのRefactorフェーズ
機能実装直後が最もリスクが低い。テストが安全網になっている。
バグ修正時
原因となった複雑さを解消する。同じバグが再発しないように。
コードレビュー後
指摘された問題をリファクタリングで解決する。

Section 08

プラクティス⑤ シンプルな設計

シンプルな設計の4つのルール（Kent Beck）

🥇 ルール1：テストをパスする
動くことが最優先。テストが通らない美しい設計は無価値。
🥈 ルール2：意図が明確である
他の開発者が読んですぐ理解できる。自己文書化されたコード。
🥉 ルール3：重複がない
DRY原則（Don't Repeat Yourself）。同じロジックを2か所以上に書かない。
🏅 ルール4：要素が最小限
クラス・メソッドの数を最小化。不要な複雑さを持ち込まない。

YAGNI原則（You Aren't Gonna Need It）

❌ YAGNIを無視した設計
「将来必要になるかも」で今実装する
「汎用性を持たせておこう」と抽象化しすぎる
「スケールするかもしれないから」と最適化する
✅ YAGNIを守った設計
今必要なものだけ実装する
具体的な要件が出てから抽象化する
実際の問題が来てから最適化する（時期尚早な最適化は万悪の元）

Section 09

プラクティス⑥ 小さなリリース

1〜2週間ごとに価値ある機能を届ける

❌ 大きなリリース（従来型）
6〜12ヶ月かけて大量機能を実装
リリース後に大量のバグ発見
ユーザーが求めていない機能が大量に
問題の原因特定が困難
フィードバックサイクルが長い
✅ 小さなリリース（XP）
1〜2週間ごとに価値ある機能を届ける
少ない変更なのでバグも少ない
ユーザーの反応をすぐに確認できる
問題があっても少ない変更から特定
素早いフィードバックで方向修正できる

全員が同じスタイルでコードを書く

目標：コードスタイルについての議論をゼロにする。自動化ツールで一貫性を保つ。

XPのイテレーションサイクル

1〜2週間のリズムで回すフロー

flowchart TD MON["月曜日：計画ゲーム\n前回の振り返り 30分\nベロシティの確認\n今回のストーリー選択\nタスク分解と見積もり"] DEV["火〜木：開発\nTDDでコードを書く\nペアプログラミング\n継続的インテグレーション\nデイリースタンドアップ 15分"] FRI["金曜日：レビュー & 振り返り\nデモ（完成した機能を顧客に）\n受け入れテストの実行\nKPT振り返り\n次のイテレーションへの準備"] MON --> DEV --> FRI --> MON

KPT 振り返りフレームワーク

✅ Keep（続けること）
良かったこと・うまくいったこと。次のイテレーションも継続する。
例：ペアプロで品質が上がった
❌ Problem（問題点）
うまくいかなかったこと。困ったこと・障害になったこと。
例：CIが遅くてストレスだった
🚀 Try（試すこと）
次回試すアイデア・改善案。担当者と期限を決める。
例：テストを並列化してCIを速くする

導入の障壁と対策

よくある障壁対策と説得材料
「TDDは時間がかかる」短期的には遅いが、長期的にはバグ修正コストが減る。データで示す。
「ペアプロはリソースの無駄」2人で書くとレビューコストが大幅削減。知識共有の副作用も大きい。
「毎日コミットするのは怖い」CIがあれば問題は自動的に検出される。まず試してみる。
「顧客が一緒にいられない」Slack・デモ環境・PO制で代替できる。フィードバック遅延を最小化する。
Section 21

XPのアンチパターンと対策

よくある失敗パターンを知り、対策する

Flaccid Scrum（貧弱なスクラム）
プロセスはスクラムだが、TDDもCIも何もやっていない。形式だけのアジャイル。
対策：具体的な技術プラクティスを導入する。
TDDのふり
テストを後から書いて「TDDをやっています」と言う。本来のTDDではない。
対策：レッド→グリーン→リファクタの順序を厳守する。
ペアプロの形骸化
片方がPCを見てもう片方がスマホを見ている状態。意味のない「ペア」。
対策：ロール交代・集中・フィードバックを徹底する。
壊れたCIの放置
「後で直す」と言ってビルドが数日間赤いまま。CIへの信頼が失われる。
対策：壊れたビルドは最優先修正をチームルールとする。
技術的負債の蓄積
「今はMVPだから」を言い訳にリファクタリングをしない。後から対処不能になる。
対策：ボーイスカウトルールを守る。常に少し良くする。
顧客との距離
ストーリーを決めたら数週間顧客と話さない。認識齟齬が積み重なる。
対策：最低週2回は顧客とコンタクトする。

Section 22

ベストプラクティス総まとめ

XP実践の黄金律10箇条

1
価値から始める
5つの価値を理解してからプラクティスを導入する。価値なきプラクティスは形骸化する。
2
TDDは最初から
後からテストを追加するのは困難。最初から習慣にする。
3
小さく早くリリース
大きなリリースより小さなリリースを。学習速度が上がる。
4
ペアを定期的に変える
固定ペアは知識の孤立を生む。毎日・毎週ローテーションする。
5
CIを神聖に扱う
壊れたビルドを最優先で修正。赤いCIを放置しない。
6
シンプルに保つ
「将来必要かも」で複雑にしない。YAGNI・KISSを守る。
7
顧客を巻き込む
技術チームだけで決めない。常にビジネス価値を確認する。
8
振り返りを欠かさない
KPTをイテレーションごとに。改善のサイクルを回す。
9
持続可能なペースを守る
残業はプロセスの失敗のサイン。計画を見直すきっかけにする。
10
全プラクティスは連携している
1つだけ導入しても効果は薄い。相互依存を理解して組み合わせる。

XP成熟度モデル

Lv.0
XP未実践 アドホックな開発。プロセスが個人依存。
Lv.1
基礎プラクティス導入 デイリースタンドアップ。バージョン管理・基本的CI。
Lv.2
技術品質の確立 TDDの実践。CI/CDの整備。コーディング規約。
Lv.3
チームプラクティスの定着 ペアプログラミング。コレクティブオーナーシップ。計画ゲーム。
Lv.4
顧客との統合 オンサイト顧客。受け入れテスト。小さなリリースの確立。
Lv.5
XPの体質化 全プラクティスが自然に機能。状況に合わせてカスタマイズ。他チームへ伝播できる。
