SECTION 01⚡

EDAとは何か？

定義・課題解決・ユースケース

💡 核心思想
「何かが起きたこと（イベント）を通知し、それに反応する。各コンポーネントは互いの存在を直接知らなくてよい。」
サービス同士はイベントを通じて間接的に通信するため、変更の影響を局所化できます。

1.1 従来のリクエスト駆動型 vs EDA

従来の同期型API連携では、注文サービスが在庫・決済・通知・配送の各サービスを順番に直接呼び出すため、1つのサービスが遅延すると全体に影響します。EDAではOrderPlacedEventを発行するだけで、各サービスが独立して非同期に反応します。

アーキテクチャ比較：リクエスト駆動型 vs EDA

1.2 EDAが解決する4つの問題

🔗
密結合 → 疎結合
サービス間の直接依存をなくし、1つの障害が全体に波及しない設計を実現。コンポーネントは互いの存在を知らなくてよい。
⏱️
同期ブロック → 非同期処理
応答を待たない設計で高スループット・低レイテンシを達成。ピーク時の負荷をイベントキューで吸収できる。
🔧
改修困難 → 拡張容易
新機能は「イベントを購読するだけ」で追加可能。既存のプロデューサーコードに一切触れない。
📈
スケール困難 → 独立スケール
コンシューマーはそれぞれ独立してスケールアウト。ボトルネックとなるサービスだけを増強できる。

1.3 EDAが適しているユースケース

EDA 適用ユースケース マインドマップ
💡 初学者向けポイント

「メール送信」「在庫更新」「決済処理」など、注文後にやるべき処理を列挙してみてください。それらが独立した「イベントへの反応」として切り出せるなら、EDAは適切なアーキテクチャです。

SECTION 02🧩

EDAの基本構成要素

Producer / Broker / Consumer とイベントの解剖

2.1 3つの主要コンポーネント

Producer → Broker → Consumer の基本関係
📤
プロデューサー（Producer）
イベントを生成・発行するコンポーネント。誰が受け取るかを知らない。

例：注文サービス、IoTセンサー、ユーザー操作イベント
🔀
ブローカー（Broker）
イベントを受け取り、保存・ルーティング・配信するミドルウェア。

例：Apache Kafka、RabbitMQ、AWS EventBridge
📥
コンシューマー（Consumer）
イベントを受信・処理するコンポーネント。処理後に新たなイベントを発行することもある。

例：在庫サービス、通知サービス

2.2 イベントの構造（Anatomy of an Event）

イベントはメタデータ（すべてのイベントに共通）とペイロード（イベント固有のデータ）の2層で構成されます。

フィールド型説明必須
event_idUUIDイベントの一意識別子。べき等性チェックに使用必須
event_typeStringイベントの種類。例: order.placed必須
occurred_atISO8601イベントが発生した日時（UTC）必須
sourceString発生元サービス名必須
versionStringスキーマバージョン。例: 1.0必須
correlation_idUUID分散トレーシング用ID。リクエスト全体を追跡推奨
ペイロードフィールドAnyイベント固有のビジネスデータ。自己完結型にする任意

2.3 イベントの実装例（Python）

Pythonevents/order_placed.py
from dataclasses import dataclass, field, asdict
from datetime import datetime, timezone
from uuid import uuid4
import json

@dataclass(frozen=True)   # frozen=True: イミュータブル（変更不可）
class EventMetadata:
    """すべてのイベントに共通するメタデータ"""
    event_id: str = field(default_factory=lambda: str(uuid4()))
    occurred_at: str = field(default_factory=lambda: datetime.now(timezone.utc).isoformat())
    version: str = "1.0"
    correlation_id: str = field(default_factory=lambda: str(uuid4()))

@dataclass(frozen=True)
class OrderPlacedEvent:
    """
    注文が確定されたことを表すドメインイベント
    設計ポイント:
      1. 名前は必ず過去形: OrderPlaced（注文が確定した）
      2. イミュータブル: frozen=True で変更不可
      3. 自己完結型: 受信者がDBを参照しなくてよい情報を含む
    """
    event_type: str = "order.placed"
    source: str = "order-service"
    metadata: EventMetadata = field(default_factory=EventMetadata)
    order_id: str = ""
    customer_id: str = ""
    customer_email: str = ""
    total_amount: float = 0.0
    currency: str = "JPY"
    items: list = field(default_factory=list)

    def to_json(self) -> str:
        return json.dumps(asdict(self), ensure_ascii=False)

# ─── 使用例 ───
event = OrderPlacedEvent(
    order_id="order_12345",
    customer_id="cust_67890",
    customer_email="user@example.com",
    total_amount=15000.0,
    items=[{"product_id": "prod_001", "name": "Tシャツ", "quantity": 2, "price": 5000}]
)
print(event.to_json())

SECTION 03📋

イベントの種類と設計

4分類・Good vs Bad・スキーマ進化戦略

3.1 イベントの4分類

🧩
ドメインイベント（Domain Event）
ビジネス上で意味のある出来事。最も重要なイベント種別。

例: OrderPlaced（注文確定）
PaymentCompleted（決済完了）
CustomerRegistered（顧客登録）
⚙️
システムイベント（System Event）
インフラ・技術的な出来事。ビジネスロジックとは分離する。

例: ServiceStarted（起動）
HealthCheckFailed（障害検知）
🔔
トリガーイベント（Trigger Event）
処理のキックオフ。スケジュール実行や手動起動の代わりに使用。

例: BatchProcessingRequested（バッチ開始）
🔄
変更通知イベント（Change Notification）
データの変更を通知。キャッシュ更新やCQRSのプロジェクション更新に利用。

例: ProductPriceChanged（価格変更）

3.2 良いイベント設計 vs 悪いイベント設計

✅ 良いイベント設計
  • 過去形で命名する: OrderPlaced（注文が確定した）← 起きた事実
  • 自己完結型にする: 受信者がDBを参照しなくてよい情報をペイロードに含める
  • イミュータブルにする: 発生した事実は変更不可。バージョンアップは新しいイベントで
  • スキーマバージョンを管理: version: "2.0"を付与し後方互換性を保つ
  • べき等性を保証する: 同じイベントを2回処理しても結果が変わらない設計
❌ 悪いイベント設計
  • 命令形で命名: CreateOrder（これはコマンドであってイベントではない）
  • IDのみを含める: order_id: "12345"だけでは受信者が毎回DBアクセスが必要
  • 巨大すぎるイベント: 50フィールド以上の「神イベント」はスキーマ変更の影響が甚大
  • バージョン管理なし: フィールド名変更などの破壊的変更で既存コンシューマーが壊れる
  • 細かすぎる粒度: UserFirstNameChangedとUserLastNameChangedを別々に送る（Chatty Events）

3.3 イベントスキーマの進化戦略

スキーマバージョニング — 後方互換 vs 破壊的変更の対処
⚠️ 破壊的変更を行う場合のルール

フィールド名の変更・型変更など破壊的な変更が必要な場合は、旧バージョンと新バージョンを並行して一定期間（目安：3ヶ月）同時発行し、すべてのコンシューマーが移行完了後に旧バージョンを廃止します。

4.3 メッセージキュー型 vs イベントストリーミング型の本質的違い

📬 メッセージキュー型（RabbitMQ / SQS）
  • 消費されたメッセージは削除される（1回限り）
  • 1つのメッセージは1つのコンシューマーのみに配信
  • タスクキュー・ワークキューに最適
  • ACK/NACKで確実な配信を保証
📊 イベントストリーミング型（Kafka / Kinesis）
  • イベントは保持期間中保存（再生・巻き戻し可能）
  • 複数のコンシューマーグループが独立して購読可能
  • イベントソーシング・リアルタイム分析に最適
  • オフセット管理でコンシューマーが処理位置を制御

SECTION 05🗺️

EDAのトポロジーパターン

仲介者 / ブローカー / Sagaパターン

5.1 仲介者トポロジー（Mediator Topology）

中央の仲介者（オーケストレーター）がワークフロー全体の制御を担当します。処理の順序・条件分岐・エラーハンドリングを一箇所で管理できますが、仲介者への依存が生じます。

仲介者トポロジー — 仲介者が処理順序を制御

5.2 ブローカートポロジー（Broker Topology）

中央制御なし。各サービスがイベントに独立して反応し、新しいイベントを発行することで処理が連鎖します。完全疎結合ですが、フロー全体の追跡が複雑になります。

ブローカートポロジー — 各サービスが自律的に反応

5.3 仲介者 vs ブローカーの使い分け

観点仲介者トポロジーブローカートポロジー
処理の制御中央集権的・順序制御可能分散・各サービスが自律
結合度仲介者への依存あり完全疎結合
エラーハンドリング仲介者で一元管理各サービスが個別に対応
可視性フロー全体が見えやすい追跡が複雑になりやすい
適用場面複雑なワークフロー・承認フロー独立したリアクション処理
代表ツールAWS Step Functions、TemporalApache Kafka、EventBridge

5.4 Sagaパターン（分散トランザクション）

マイクロサービス間でデータの整合性を保つパターン。各サービスがローカルトランザクションを実行し、失敗時は補償トランザクション（Compensating Transaction）で前の状態に戻します。

Saga（Choreography型）— 正常フローと補償トランザクション
⚠️ Sagaの注意点：結果整合性（Eventual Consistency）

Sagaでは厳密なACID整合性ではなく結果整合性を採用します。一時的に各サービスの状態が不一致になる可能性があり、UXやビジネスロジックでこれを考慮する必要があります。

6.1 Kafkaのアーキテクチャ概観

Kafkaクラスター全体図（Broker / Topic / Partition / Consumer Group）

6.2 Kafkaの主要概念

Topic（トピック）
メッセージのカテゴリ
例：orders/payments
複数のPartitionで構成される
Partition（パーティション）
並列処理の基本単位
順序保証はPartition内のみ。Partition数がスループットの上限を決める
Offset（オフセット）
メッセージの位置番号
コンシューマーが管理。任意の位置から再生可能（巻き戻し可能）
Consumer Group
水平スケールの単位
同一グループ内でPartitionを分担。グループ間は独立して購読
Replication Factor
レプリカ数（通常3）
LeaderがI/Oを担当。障害時はFollowerが昇格（高可用性）
Retention（保持期間）
デフォルト7日間
時間/サイズベースで設定。Log Compactionで最新値のみ保持も可能

6.3 Kafkaの実装例（Python）

Pythonkafka/producer.py — プロデューサー
from kafka import KafkaProducer
from kafka.errors import KafkaError
from uuid import uuid4
from datetime import datetime, timezone
import json, logging
logger = logging.getLogger(__name__)

class OrderEventProducer:
    def __init__(self, bootstrap_servers: list[str]):
        self._producer = KafkaProducer(
            bootstrap_servers=bootstrap_servers,
            value_serializer=lambda v: json.dumps(v, ensure_ascii=False).encode("utf-8"),
            key_serializer=lambda k: k.encode("utf-8") if k else None,
            acks="all",            # すべてのレプリカへの書き込み確認を待つ
            retries=3,             # 失敗時のリトライ回数
            retry_backoff_ms=100,
            batch_size=16384,      # バッチサイズ（16KB）
            linger_ms=10,          # バッチ待機時間（throughput向上）
            compression_type="gzip",
        )

    def publish_order_placed(self, order: dict) -> None:
        event = {
            "event_type": "order.placed",
            "event_id":   str(uuid4()),
            "occurred_at": datetime.now(timezone.utc).isoformat(),
            "version":    "1.0",
            "order_id":   order["id"],
            "customer_id": order["customer_id"],
            "total_amount": order["total_amount"],
            "items":      order["items"],
        }
        try:
            # order_id をキーにすることで同じ注文のイベントが
            # 同じパーティションに送られ、順序が保証される
            future = self._producer.send(
                topic="orders",
                key=order["id"],    # ← パーティションキー（順序保証）
                value=event,
            )
            meta = future.get(timeout=10)  # 同期待機（送信確認）
            logger.info(f"発行成功: partition={meta.partition}, offset={meta.offset}")
        except KafkaError as e:
            logger.error(f"発行失敗: {e}")
            raise

    def close(self):
        self._producer.flush()
        self._producer.close()
Pythonkafka/consumer.py — べき等なコンシューマー
from kafka import KafkaConsumer
import json, logging
logger = logging.getLogger(__name__)

class InventoryEventConsumer:
    def __init__(self, bootstrap_servers: list[str]):
        self._consumer = KafkaConsumer(
            "orders",
            bootstrap_servers=bootstrap_servers,
            group_id="inventory-service",    # コンシューマーグループID
            value_deserializer=lambda v: json.loads(v.decode("utf-8")),
            auto_offset_reset="earliest",    # 初回は最初から読む
            enable_auto_commit=False,        # 手動コミット（確実な処理のため）
            max_poll_records=100,
        )

    def start(self):
        try:
            for message in self._consumer:
                try:
                    self._process_event(message.value)
                    self._consumer.commit()  # 処理成功後にオフセットをコミット
                except Exception as e:
                    logger.error(f"処理エラー: {e}")
                    self._send_to_dlq(message.value, str(e))
        finally:
            self._consumer.close()

    def _process_event(self, event: dict):
        if event.get("event_type") != "order.placed":
            return
        # べき等性チェック: 同じevent_idを2度処理しない
        if self._already_processed(event["event_id"]):
            logger.info(f"重複イベントをスキップ: {event['event_id']}")
            return
        self._reserve_stock(event["order_id"], event["items"])
        self._mark_as_processed(event["event_id"])  # Redisなどで管理

    def _already_processed(self, event_id: str) -> bool:
        return False  # 実際はRedis等で処理済みIDを管理

    def _reserve_stock(self, order_id: str, items: list):
        for item in items:
            logger.info(f"在庫引当: {item['product_id']} x {item['quantity']}")

    def _mark_as_processed(self, event_id: str): pass
    def _send_to_dlq(self, event: dict, error: str):
        logger.error(f"DLQへ送信: error={error}")
✅ Kafkaベストプラクティス

パーティション数 ≧ コンシューマーグループの最大コンシューマー数を守ること。パーティション数 < コンシューマー数の場合、余分なコンシューマーはアイドル状態になります。キーベースのパーティショニング（例：order_idをキーに設定）で同一エンティティのイベント順序を保証します。

7.1 EventBridgeのアーキテクチャ

AWS EventBridge — ソース → バス → ルール → ターゲット
🚌
イベントバス（Event Bus）
Default（AWSサービス用）、Custom（自作アプリ用）、Partner（SaaS用）の3種類。
📋
イベントルール（Event Rule）
JSONパターンマッチングでフィルタリング。数値範囲・文字列マッチ・存在チェックが可能。
📐

イベントスキーマを自動検出・保存。SDK用コードを自動生成でき型安全を実現。

7.2 EventBridgeの設定例（Terraform HCL）

HCLeventbridge/main.tf
# カスタムイベントバスの作成
resource "aws_cloudwatch_event_bus" "orders" {
  name = "orders-event-bus"
}

# 注文確定イベントを在庫LambdaへルーティングするRule
resource "aws_cloudwatch_event_rule" "order_to_inventory" {
  name           = "order-placed-to-inventory"
  event_bus_name = aws_cloudwatch_event_bus.orders.name

  # イベントパターン: source + detail-type でフィルタリング
  event_pattern = jsonencode({
    source      = ["com.myapp.order-service"]
    detail-type = ["OrderPlaced"]
    detail = {
      total_amount = [{ numeric = [">=", 1000] }]  # 1000円以上のみ
    }
  })
}

# ターゲット（Lambda）の設定
resource "aws_cloudwatch_event_target" "inventory_lambda" {
  rule           = aws_cloudwatch_event_rule.order_to_inventory.name
  event_bus_name = aws_cloudwatch_event_bus.orders.name
  target_id      = "InventoryServiceLambda"
  arn            = aws_lambda_function.inventory_service.arn

  dead_letter_config {           # 失敗時のDLQ設定（必須！）
    arn = aws_sqs_queue.event_dlq.arn
  }
  retry_policy {
    maximum_event_age_in_seconds = 3600  # 最大1時間リトライ
    maximum_retry_attempts       = 3
  }
}
✅ EventBridge ベストプラクティス

ターゲットには必ずDead Letter Queue（DLQ）を設定すること。設定しない場合、処理失敗したイベントは永遠に失われます。またsourceには"com.myapp.service-name"、detail-typeには"OrderPlaced"のような具体的な値を設定し、ルールのスコープを明確にします。

SECTION 08📜

イベントソーシング（Event Sourcing）

状態ではなく「イベントの履歴」を唯一の真実（Single Source of Truth）とする

💡 イベントソーシングの核心
従来のDBは「現在の状態」のみを保存します。イベントソーシングでは「状態を変化させたすべてのイベントの履歴」を保存し、現在の状態はイベントを再生（リプレイ）して導出します。これにより完全な監査ログ・タイムトラベル・バグ再現が可能になります。

8.2 イベントソーシングの実装例（Python）

Pythondomain/order_aggregate.py
class OrderAggregate:
    """
    イベントソーシングによる注文集約。
    状態変更はイベントを通じてのみ行う。
    現在の状態はイベントの再生から導出する。
    """
    def __init__(self, order_id: str):
        self._id, self._status, self._items = order_id, "INITIAL", []
        self._total, self._version = 0.0, 0
        self._uncommitted_events: list[dict] = []

    # ── コマンドハンドラー（ビジネスルールを検証してイベントを生成）──
    def create(self, customer_id: str):
        if self._status != "INITIAL":
            raise ValueError("すでに作成済みです")
        self._apply_and_record({"event_type": "OrderCreated", "customer_id": customer_id})

    def add_item(self, product_id: str, name: str, price: float, qty: int):
        if self._status != "PENDING":
            raise ValueError("PENDING状態でのみ商品を追加できます")
        self._apply_and_record({"event_type":"ItemAdded","product_id":product_id,
                                 "name":name,"price":price,"quantity":qty})

    def confirm(self):
        if not self._items: raise ValueError("商品が1件もありません")
        self._apply_and_record({"event_type": "OrderConfirmed"})

    def cancel(self, reason: str):
        if self._status in ("SHIPPED", "DELIVERED"):
            raise ValueError("発送済みはキャンセルできません")
        self._apply_and_record({"event_type": "OrderCancelled", "reason": reason})

    # ── イベントアプライヤー（純粋な状態更新・副作用なし）──
    def _apply_event(self, event: dict):
        t = event["event_type"]
        if t == "OrderCreated":   self._status = "PENDING"
        elif t == "ItemAdded":
            self._items.append(event)
            self._total += event["price"] * event["quantity"]
        elif t == "OrderConfirmed": self._status = "CONFIRMED"
        elif t == "OrderCancelled": self._status = "CANCELLED"
        self._version += 1

    def _apply_and_record(self, event_data: dict):
        self._apply_event(event_data)
        self._uncommitted_events.append(event_data)

    @classmethod
    def rebuild_from_events(cls, order_id: str, events: list[dict]):
        """保存されたイベント履歴から集約を再構築する（リプレイ）"""
        agg = cls(order_id)
        for ev in events:
            agg._apply_event(ev)  # ビジネスルールを通さず直接適用
        return agg

8.3 スナップショット戦略（パフォーマンス最適化）

イベント数が増えるにつれ集約の再構築に時間がかかります。一定間隔（目安：100件ごと）でスナップショット（その時点の状態）を保存することで、スナップショット以降のイベントのみ再生すればよくなります。

SECTION 09⚖️

CQRS（コマンドクエリ責務分離）

Command Query Responsibility Segregation

💡 CQRSの原則
「書き込み（Command）」と「読み取り（Query）」のモデルを分離します。書き込みは整合性を重視した正規化DBに、読み取りは参照に最適化した非正規化DBに行います。EDAでイベントを使って両者を非同期同期することで、書き込みスケールと読み取りスケールを独立して最適化できます。

9.1 CQRS + EDA + Event Sourcing の組み合わせ

EDA + CQRS + Event Sourcing — コマンドサイドとクエリサイドの完全分離

9.2 いつCQRSを使うべきか

✅ CQRSが適している場合
  • 読み取りと書き込みの負荷バランスが大きく異なる（例：読み取り10倍）
  • 読み取りに複数の最適化されたビューが必要（全文検索 + RDB + キャッシュ）
  • 複雑なビジネスドメインでEvent Sourcingと組み合わせる
  • マイクロサービスで各サービスが自身の読み取りモデルを持つ
❌ CQRSが不適な場合
  • シンプルなCRUDアプリケーション（過剰設計になる）
  • チームが小さく、複雑さを管理できない
  • 結果整合性（Eventual Consistency）をUXに組み込めない
  • 読み取りと書き込みの負荷がほぼ同じ場合

SECTION 10🛡️

エラーハンドリングと信頼性設計

DLQ / サーキットブレーカー / リトライ戦略 / べき等性

10.1 配信保証モデルの選択

📬
At-Least-Once（最低1回）
最も現実的な選択。少なくとも1回は届けるが重複する可能性がある。べき等なコンシューマーで対処する。Kafka・SQSのデフォルト。
🎲
At-Most-Once（最大1回）
重複は起きないがメッセージロストの可能性がある。ログ収集など損失許容可能な場面のみ。
🎯
Exactly-Once（正確に1回）
Kafka EOS（Exactly-Once Semantics）で実現可能だが実装コストが高い。決済など重複不可の場面で使用。

10.2 Dead Letter Queue（DLQ）パターン

DLQパターン — 処理失敗メッセージの安全な隔離と再投入
🚨 DLQは必ず設定すること

DLQを設定しないと、処理に失敗したイベントが永遠に失われます。DLQのメッセージ数を常時ゼロになるよう監視し、増加時は即座にアラートを出すことが重要です。

10.4 指数バックオフ + ジッターによるリトライ

Pythonutils/retry.py — 指数バックオフ + ジッターデコレーター
import time, random, logging
from typing import Callable, Any
from functools import wraps
logger = logging.getLogger(__name__)

def exponential_backoff_retry(
    max_retries: int = 3,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    jitter: bool = True,        # Thundering Herd問題を防ぐランダム要素
    exceptions: tuple = (Exception,),
):
    """
    指数バックオフ + ジッターによるリトライデコレーター

    ジッターを加えることで、複数のコンシューマーが同時にリトライして
    サービスに負荷が集中する「Thundering Herd問題」を防ぐ。
    待機時間: 1s → 2s → 4s → 8s（最大max_delay秒まで）
    """
    def decorator(func: Callable) -> Callable:
        @wraps(func)
        def wrapper(*args, **kwargs) -> Any:
            last_exc = None
            for attempt in range(max_retries + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    last_exc = e
                    if attempt == max_retries:
                        logger.error(f"最大リトライ到達: {func.__name__}, error={e}")
                        raise
                    delay = min(base_delay * (2 ** attempt), max_delay)
                    if jitter:
                        delay = delay * (0.5 + random.random())  # ±50%のランダム要素
                    logger.warning(f"リトライ {attempt+1}/{max_retries}: {delay:.2f}秒後")
                    time.sleep(delay)
            raise last_exc
        return wrapper
    return decorator

# ─── 使用例 ───
@exponential_backoff_retry(max_retries=3, base_delay=1.0)
def process_order_event(event: dict) -> None:
    """注文イベントを処理する（自動リトライ付き）"""
    inventory_service.reserve_stock(event["items"])

EDAのセキュリティ設計

11.1 EDAセキュリティの4レイヤー

🔑
認証（Authentication）
誰がイベントを発行しているかを検証する。

実装手段： サービスアカウント、mTLS（相互TLS）、JWT/OAuth2トークン。各サービスに一意のIDを付与し、なりすましを防ぐ。
🛡️

何のトピックに書き込み・読み取りできるかを制御する。

🔐

転送中・保存中のデータを暗号化する。

実装手段： TLS 1.2以上での転送暗号化、AES-256での保存時暗号化、PIIのフィールドレベル暗号化。
📋
スキーマ検証 + 監査ログ
不正なイベントの注入を防ぐ。

実装手段： Schema Registry（Confluent）でスキーマ検証。すべてのイベントの送受信を監査ログに記録しコンプライアンスを満たす。

11.2 個人情報（PII）の取り扱いパターン

PII種別推奨対処実装例

SECTION 15⚠️

EDAのアンチパターン

やってはいけない設計と、その修正方法

15.1 主要な4つのアンチパターン

❌ Anti-Pattern 1: Event Sourcingの乱用
すべてのデータにEvent Sourcingを適用してしまう。シンプルなCRUD（ユーザー設定、マスタデータ）に適用しても過剰な複雑さを生むだけで、メリットはほとんどない。
✅ 解決策
複雑なビジネスロジックを持つ集約（注文、取引）のみに限定する。参照データ・マスタデータには通常のRDBを使用する。「本当にイベント履歴が必要か？」を常に問う。
❌ Anti-Pattern 2: Chatty Events（過剰なイベント）
細かすぎるイベントを大量に発行する。UserFirstNameChangedとUserLastNameChangedを別々に発行→受信者が毎回複数の更新処理が必要になる。
✅ 解決策
ビジネス上意味のある粒度に統合する。UserProfileUpdatedとして変更されたフィールドをまとめてペイロードに含める。「ビジネスとして何が起きたか」を1イベントで表現する。
❌ Anti-Pattern 3: Synchronous Thinking（同期的な思考）
EDAを採用しているのに同期的な応答を期待する設計。在庫サービスの完了を待つ実装→EDAのメリットを打ち消す。結果整合性を理解していない。
✅ 解決策
結果整合性（Eventual Consistency）をUX設計に組み込む。注文確定後はorderId返却のみ行い、ステータス更新はWebSocket/SSE/ポーリングで通知する設計にする。
❌ Anti-Pattern 4: God Event（神イベント）
1つのイベントに50以上のフィールドを詰め込むOrderSuperEvent→スキーマ変更の影響が甚大になり、受信者が不要なデータを受け取る。
✅ 解決策
責務を分割した複数のイベントに分ける。OrderPlaced、PaymentProcessed、ShipmentCreatedを別々のイベントとして発行する。各イベントは自己完結型を保つ。
